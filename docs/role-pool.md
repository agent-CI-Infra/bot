# Role-Pool and task coordination

Tasks retain goals, criteria, candidates and final delivery authority. A project can opt into role coordination without changing its existing queue, GitHub event entry points, policy validation or publisher. Existing projects remain on their previous executor until enabled; QA always runs as a recorded role with a fresh evaluation context.

## Configuration and execution

`GET/PUT /api/repositories/:repository/roles` uses existing project administration grants; the console 「角色」 page and later management entry points call the same service. A PUT carries `expected_revision` (the current revision, `0` before the first save) and the full RoleDefinitionV2 configuration:

```json
{"expected_revision":3,"enabled":true,
 "controller":{"role":"manager","entries":{"development":true,"request":true,"review":true,"actions":false}},
 "skills":[{"id":"review-kit","source":{"type":"repository","commit":"<40-hex sha>","paths":[".agents/skills/review/SKILL.md"]}}],
 "roles":[{"role_id":"reviewer","harness_ref":{"id":"process"},"model_profile_ref":{"model_id":"<model id>"},"skill_bundle_ref":{"id":"review-kit"},"persona_prompt":"Focus on input boundaries."}]}
```

Each role has `role_id`, `revision`, name, responsibility, persona prompt and fixed-version references: `model_profile_ref`, `skill_bundle_ref`, `harness_ref`, `capability_policy_ref`, `environment_profile_ref`, `budget_policy_ref` and `output_schema_ref`. Omitted roles and fields take built-in defaults. A save is validated field by field; an error returns its code and the failing `field`, for example `roles.reviewer.harness_ref.id`. A stale `expected_revision` returns 409. Each save becomes an immutable revision; `?revision=N` returns an older one. A role's own `revision` moves only when its definition changes.

- Model profiles reference a model this project may use by id and pin its endpoint and model name (`profile_hash`); the key stays sealed in the model store and is never part of a definition or snapshot. A rotated key keeps the profile; a changed endpoint or name is rejected as `role_model_profile_changed`.
- Skill bundles pin their source and files: built-in guides by content, repository skills from the rule cache at exactly the named commit (refresh the project rules first), or console files. Every file has its path, size and sha256, and the bundle a content hash; the stored contents never follow a moving path. Skills are working material. A role reads them with `read_skill`; each read is recorded with bundle revision and file hash. Playbooks stay optional advice; no skill or playbook adds a stage, a tool or authority.
- Capability policies, environment profiles, budget policies and output schemas are server catalog entries with content-hash versions. A role's kind bounds what it may select: the controller `controller`, `dev` the entry's writer profile, observers `observer` or the narrower `observer-readonly`, QA `evaluator`. Budgets can only lower an entry's limits. The persona prompt is data: changing it never changes tools, authority or the task contract. The controller and QA cannot be disabled.
- The Harness capability matrix lists the role kinds, model API, tool-call and structured-output support of each driver. `native`, `process`, `acp` and `pi` are peer Agent backends and can run controller, writer, observer and evaluator roles. New configurations recommend Pi for every role; each role can explicitly select another supported backend. Backend selection never changes its tools or authority. The console and API list `claude_code` as an available worker backend; the planned Codex and OpenCode drivers remain unavailable. `acp` and the pinned Claude Code adapter bring their own model (`externalModel`): no project model is resolved for either backend, snapshots record the model source as `external_harness`, and a `model_profile_ref` on either backend is rejected at `roles.<id>.model_profile_ref`. A combination outside the matrix is rejected when saving and again before a run starts; no other model, provider or driver is substituted. `claude_code` currently declares only writer, observer and evaluator capabilities, so manager and coordinator are refused at save and resolve time, including legacy bindings and explicit overrides. Its model gateway validates run tokens in-process; external gateway profiles are unsupported (see [Claude Code](claude-code.md)). Every driver runs through the shared cancellable session of [Harness Runtime](harness-runtime.md); a cancelled run ends as `harness_cancelled`.

Models resolve in order: the role's explicit profile, then the workflow's model, then the project default. `POST .../roles/resolve` previews the exact run snapshot without storing anything or creating a task. A run stores its snapshot by content hash (`role_snapshots`, also readable as task source `role_snapshots:<hash>`): actual model id/version/name and its source, skill files and hashes, harness id/version and runtime package, capability policy and tools, environment, budget and output schema. Configurations saved before RoleDefinitionV2 keep running unchanged, with a native manager, until they are saved again.

With coordination enabled, the entries switched on in `controller.entries` run under the project controller with its selected backend. Development and ordinary requests use Manager → selected role runs → nominated delivery → independent QA → existing delivery/publisher. Review and Actions failure analysis retain their entry-specific tools, workspace and completion as the `dev` assignment, using that role's configured backend subject to the old-V2 compatibility rule below; the controller delegates it, reads its result by reference and nominates it, and the existing publication and QA follow. Each attempt records a `controller_entry` event with the configuration revision. Tasks keep their id, contract, candidate and history when an entry is switched either way; other workflows keep their established executor.

The controller runs on its configured backend. Pi sessions use an empty workspace on the project computer and forward only the offered tools to the control plane. Native/Process/ACP use the same controller tools and result validators through their own runtime. Each run is bounded; a role backend cannot grant itself product or publication tools. It only has task record, progress, playbook and delegation tools, all executed by the control plane through the runner's control mailbox. It cannot edit product files, run commands, publish, accept, complete, override QA, merge or grant permissions. A call to any other tool, delegation to QA, the controller itself or an unoffered role, and a delegation carrying extra fields (tools, models, permissions) are refused and recorded as `capability_denied`. Prompts, repository content and CLI output cannot change these checks. `nominate_delivery` selects the latest dev output for QA; it does not change task status to completed. Custom roles follow the observer result contract. Dev is the only writable role; observers receive separate disposable checkouts of a fixed dev snapshot. Their command side effects do not become the delivery tree. Each formal QA evaluation is fresh, even though its role instance and previous evidence remain queryable.

### Console presentation

The 「角色」 page shows, in order: whether coordination is on and which entries run under the controller, with the roles each entry may delegate (development and requests: the enabled worker roles; review and Actions analysis: Dev only, on the entry's own Pi executor; every other entry and workflow keeps its executor, and independent QA accepts either way); how the Manager delegates Dev, Test, Reviewer and UX, with each role's harness and resolved model; the resolution table; and the JSON editor. This is a description of the division of work, not a fixed flow or a grant. QA is never delegated: it accepts the candidate the controller nominates. New configurations show the controller on Pi. A pre-V2 configuration with coordination on is marked as the old configuration still in use (its Native controller) until it is saved; one with coordination off runs no controller and shows the Pi controller a save would give it. The editor offers `pi` for the controller of any pre-V2 configuration, so a save upgrades it.

Each workflow's summary on the workflows page names who executes it from the same configuration, with the roles its entry actually offers. A task's detail opens with one sentence on who is doing what now, directly under its title on every screen width; a running QA run (`role: qa` in the task's runs) is named as such whatever the task's phase, since development and review start QA from inside their executor. The side panel then shows the goal, candidate, evidence, acceptance and publication from the task record, and the delegations actually recorded: `GET /api/tasks/:id/roles` is read until `next_after` is null, purposes come from `role_handoff` events, and each delegation shows the harness of every run that executed it, so a later rebinding of the role instance does not rewrite the past. If a page cursor stops advancing, the page says the records are incomplete instead of naming who is at work. Nothing there is inferred from a workflow flowchart; a task that did not run under the controller says it ran on the original executor.

### Revisions of running roles

A running run keeps the snapshot it started with. The next assignment of an instance resolves the current revision first and records `role_revision_applied` (`reason: delegation`). To move a running role, `POST /api/tasks/:id/roles/apply` with `role` and `expected_revision` marks the instance: at its next safe checkpoint (a turn boundary where every tool result is recorded) the run ends with `role_revision_checkpoint`, and the same task, instance and assignment continue on the new revision (`reason: checkpoint`, naming the ended run). Old runs remain explainable through their snapshot and the stored configuration revision. Revocation is live: disabling a role, switching coordination off or narrowing its policy stops the next capability call with `role_authority_revoked`; project disablement and model withdrawal stop runs as before.

## Shared handoff and continuing context

All role prompts require task-first collaboration: query the contract, candidate and relevant records before starting/resuming; record factual results and next actions; prefer references to duplicated prose; distinguish claims from observations and decisions; keep unknowns explicit; never persist private reasoning.

`delegate_role` carries purpose and record references. It returns a role result source, not a copied report. `read_task_record` supports paged original task-history sources, `task:<this task id>`, and the current `contract:revision:<n>`. Invalid references return correctable tool errors. History, source and run routes remain the common query surface. `GET /api/tasks/:id/roles` exposes instances and assignments, excluding conversation bodies.

One `(task, role)` instance persists its conversation and sequence. Review findings return to the same dev instance. `RoleInstance` is the role identity within a task, `assignment_id` one delegation, and each `task_runs` row one actual execution attempt with its `recovery_mode`: `checkpoint_transcript` (native/process transcript restore), `native_resume` (the Pi controller reattached to its session still living in its workspace after a control-plane crash, or an ACP agent that restored its external session), `rebuilt_from_task_records` (a fresh session from task records when the previous one is gone, was cancelled or already ended), `new_session` or `fresh_evaluation` (QA). An ACP run starts as `external_session_pending` until the agent binds its session. Interrupted tool batches are marked as missing observations; the role must query durable facts before repeating actions. Native/Process restore transcript checkpoints without automatic compaction. Pi enables SDK compaction and can reattach a surviving session after a control-plane interruption; ended sessions rebuild from durable task records. Backend recovery modes are recorded as observed, never inferred from a role name.

`role_instances` stores the pinned snapshot, revision, harness and redacted transcripts; `role_assignments` links delegation and result records; `task_runs` adds role, definition version, instance, assignment, harness/version, recovery mode and snapshot. `GET /api/tasks/:id/roles` returns instances, assignments, role runs and their snapshots. Role input/output, handoff, record reads and candidate snapshots are factual task history events. Existing tracing and model accounting remain authoritative for actual requests and tools.

## Harnesses and memory

`pi` (src/agent/pi.ts) is the Pi SDK session in a project computer workspace, driven through the runner mailbox; before a session starts the runner reports its installed Pi version, which must equal the pinned harness version (`harness_version_mismatch` otherwise), and `harness_started` records both. Model requests still go through the control plane's provider boundary, and every tool the session did not natively own is a control-plane tool. `native` uses the control-plane tool loop. `process` launches an independent Node worker which owns its conversation loop and uses JSON-line RPC for model requests, tool observations and checkpoints. The worker receives no provider/GitHub credential or inherited control-plane environment; the parent validates offered tools and retains the provider/accounting boundary. Both use the project's configured model; these are different running implementations, not model-name aliases. This process boundary is not an OS security sandbox.

Role memory reuses project memory tables and versions with `scope.role`. Default project search excludes role-scoped entries; `GET .../memories?role=dev` queries the role namespace. Roles receive a bounded index and can use `search_role_memory`, `read_project_memory` and, where otherwise allowed, `remember_role_memory`. Actual reads remain recorded; context inclusion is not proof of reading. Agent notes remain unverified and cannot overwrite human facts. Tasks in different projects remain isolated.

## Authorized merge

`POST /api/tasks/:id/merge` accepts `expected_sha` and `merge_method` (`merge`, `squash`, `rebase`). This is an explicit authorized operator action, never an agent or Manager tool. The framework requires an accepted current candidate, completed PR delivery, unchanged verification policy, the exact owned PR head and default target. It inspects remote check runs/statuses, rejects failures/incomplete checks and lets GitHub enforce repository rules. Required merge queues are not bypassed; a GitHub refusal is surfaced. Repeated/uncertain writes reuse the existing publication effect ledger and reconcile the actual merged PR.

Repositories with no remote checks are marked `no_remote_checks`; this is not CI success. Their task's required local policy and QA must still have passed. A confirmed merge produces a `repository_evolved` event with the merge SHA; later tasks prepare from the updated default branch. This endpoint does not deploy, release or confer future merge authority on a role.

Provider reasoning/thinking fields are excluded from worker messages and persisted role transcripts, matching the native loop; existing role transcripts are scrubbed on storage initialization. The shared provider boundary retries interrupted/malformed streams within its finite transport budget before returning retry_wait. This does not turn invalid business output into a pass or repeat an already acknowledged role tool operation.

Trusted integrations can add a driver through `registerRoleHarness(metadata, adapterFactory)`, declaring version, session recovery and event visibility. Project configuration can only select registered IDs; it cannot upload arbitrary executable code. Built-in drivers cannot be replaced by registration. Runtime rows record the selected driver's version independently of the pinned role prompt.
A registered driver can declare `session: task_records` when it cannot continue a transcript. The framework supplies task references, starts a fresh driver context and records `rebuilt_from_task_records` on subsequent calls. It does not label that path a continued conversation. Native process/PID resumption is not part of this first adapter contract.

Role observations tolerate an evidence string by wrapping the unchanged text in a one-element evidence array, with a normalization event. Other submission-format errors get at most two local corrections in either harness, reusing existing observations. No acceptance verdict or completion boolean is weakened. Failed/interrupted assignments are marked accordingly; a resumed role is offered its prior failed submission source so it can repair packaging without repeating unchanged checks.

统一会话生命周期与外部 ACP 执行器接入见 [Harness Runtime](harness-runtime.md)；每次运行的协议、准入、隔离环境 profile（`isolated-workspace`、`isolated-candidate`）和累计预算 `metered` 见 [RoleRun 协议](role-run.md)。第一阶段验证 Codex ACP；Native/Process 继续支持，角色结果仍由独立 QA 验收。

### Parallel integration and durable merge requests (#183)

A changed default-branch SHA no longer prevents an accepted development candidate from opening a PR. SHA identifies evidence; it does not serialize development. Each task retains its workspace and claim. Local execution accepts the same 1–32 task concurrency setting as the task scheduler (host-user isolation, no new OS sandbox or per-task quotas).

`POST /api/tasks/:id/merge` now persists explicit operator intent. A response may be `{merged:false,status:"integrating"}` or `status:"queued"`; only `merged:true`/`repository_evolved` confirms repository evolution. `GET` on the same route queries its state, expected head, contract revision, wait/error and next poll; `DELETE` withdraws the intent and dequeues an outstanding queue entry. A merge already completed cannot be undone by cancellation. Workers/controllers still have no merge tool. Permission/policy changes, an unexpected PR head or contract revision prevent automatic merge.

Without a merge queue, an advanced base triggers a new task attempt on current main. The framework preserves the original candidate as a source snapshot and three-way integrates it in a separate workspace. A clean combination runs the project's required verification and independent fresh QA without calling Dev again. A textual conflict or failed combined test returns the integrated checkout and exact event references to the same Dev instance; new delivery is checked again. The branch update retains the previous PR head as a parent and uses a versioned effect key, so it is fast-forward and does not replay a previous publication. Existing checks and GitHub protections still apply. Short merge decisions for a repository are serialized; development and integration remain parallel. External actors can advance a branch during a final GitHub API request; repositories needing atomic combined CI must enforce it through their GitHub queue/rules.

With a required merge queue, Bot enqueues the approved owned head and records GitHub's reported base/combined commits. Queue reordering or a changing combined SHA does not redevelop the feature. Failed combination checks return evidence to integration/repair; unexplained removal is surfaced for operator attention rather than silently undoing a person's dequeue. Empty remote checks remain `no_remote_checks`, never fabricated CI success.

`task_merge_requests` is coordination metadata, not another completion authority. Intent, integration source/target/tree, policy observations, candidate/QA and actual merge retain their task-history links. Pending work resumes through TaskEngine after a restart; legacy `base_branch_changed` tasks with retained snapshots are recovered automatically. Checkpoints preserve partial integration repairs. New code/memory observations use the execution baseline separately from the owned PR head. Old QA cannot certify a new integrated candidate; contract changes or unowned head updates cannot inherit merge intent. The OpenToday experiment's original long stall and manual recovery remain historical facts.

The default-branch ref is read directly before deciding whether integration is needed and before a direct merge. A PR's `base.sha` is metadata and may lag the live branch; it must not trigger repeated verification against an already integrated base. The candidate retains its source workspace independently of later execution workspaces. Stale background poll results cannot overwrite a newer integration or cancellation state.

### Planning scope differences

`contract.scope` is a planning expectation, not a file allowlist. Existing records retain this meaning without migration. Explicit user prohibitions (`contract.constraints` when provided), the goal/criteria and framework tool permissions remain binding. The Dev can use `record_scope_difference` to retain paths, necessity, relation to the goal, risk/impact, verification references and the actual tree/artifact `source_version`. Review checks the explanation against the diff; fresh QA independently judges it. Missing explanations or product defects normally return to execution; exceeding a planned file list alone does not justify `needs_human`. No extra approval gate is added. QA receives explanations with an explicit version-match flag; a match is not proof and an old explanation cannot certify a new candidate.

### On-demand Task Coordinator

Concrete cross-task issues use a persistent request, not a synchronous wait on an occupied task slot. The restricted Coordinator sends advice for the affected Task Managers to acknowledge; it cannot execute code, change acceptance criteria, override QA or merge. Requests survive restart and only explicit requests wake the worker. See [coordination lifecycle and query API](task-coordination.md). Planning scope differences alone still use the normal Dev → Review → QA path.

## Unified Agent backend selection

`GET .../roles` returns `backends` and `recommended_backend` alongside the existing `harnesses` capability matrix. Each role has a backend selector; advanced JSON retains `harness_ref` for compatibility. New configurations default to `pi`; stored legacy/V2 choices and active snapshots are not silently migrated. An omitted backend on an existing V2 role retains its current choice. All remaining role fields keep the configuration API's full-replacement semantics.

Older V2 configurations used Pi for the controller-managed review and Actions `dev` assignments, even when the saved writer default was `native`. These entries keep Pi and snapshot source `entry_executor` until a save changes the dev harness id. Reading configuration never writes a migration, and resubmitting the same id (including a normal console save) or omitting it does not opt in. A role without a previously saved V2 harness, including a new configuration or the first save of a legacy configuration, adopts its selected backend immediately. The server persists `entry_harness_source: "role"` on dev once adopted; subsequent unchanged saves retain it. The console explains when these entries still use Pi despite the saved role backend. This compatibility rule does not affect development teams, ordinary RoleRuns, QA or Coordinator. Fixed task configurations and active snapshots retain their backend until the existing explicit configuration/role-apply mechanism adopts a newer revision.

Native and Pi review/Actions dev assignments can write project notes at `../notes/<name>` through the runner's note protocol. Invalid note names return tool errors, and repository writes remain forbidden unless the workflow grants them. In this entry, a `TaskError` from a tool callback is returned as a tool error; completion validation and other run stop conditions retain their existing behavior.

Pi worker tools are executed by the same control-plane callbacks as Native: Dev writes its task workspace, observers inspect a disposable fixed candidate, and QA always gets a fresh session and the acceptance checkout. The SDK session itself has a separate empty workspace; no implicit shell, extensions or host skills are added. Coordinator uses the same role configuration and prepares a project-computer session only when Pi is selected.

`claude_code` is a registered worker backend for writer, observer and evaluator roles; it cannot run controller roles, including Manager and Coordinator (see [Claude Code](claude-code.md)). `codex` and `opencode` remain visible as pending integrations (#171 and #172). Selecting either before registration returns `agent_backend_unavailable` at `roles.<id>.harness_ref.id`. Codex over the already integrated generic ACP remains usable by selecting `acp` with the trusted ACP deployment configuration; it is not presented as the unfinished native Codex App Server driver.
