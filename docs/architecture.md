# 架构与行为

本文说明控制面、权限、虚拟电脑以及检视和开发的工作方式。部署见[部署细节](deployment.md)，接口见[管理 API](api.md)，开发与测试见[开发与验证](development.md)，接入向导和规则文件见 [Onboarding](onboarding.md)。



## 概览

一个 Node.js 22.13+ / TypeScript 控制面，使用系统内账号管理多个 GitHub App、机器人账号、仓库权限、模型配置和 Webhook 投递。

当前提供多账号控制面、每仓库一个长期 Docker 环境，以及可读代码、运行命令和修改文件的检视／开发 Agent。没有内置账号或仓库；开启仓库检视后接收事件并创建任务，满足开发条件时自动实现、测试、发布 bot 分支和 PR。`/api/status` 的项目环境、检视、开发及模型调用能力均可用；具体任务缺配置或失败会显示故障状态。

检视和开发由固定版本 Pi SDK 在项目长期容器内运行。能写 GitHub 的凭据和模型 Key 仅在控制面；Pi 的 loopback 模型入口通过任务专属 runner 邮箱请求控制面代理，没有跨项目共享服务或新增公网端口。模型需要自己读 GitHub 时（Issue、PR、评论、行内检视、Actions 运行、检查状态等），调用 `github_read_token` 经同一邮箱向控制面兑换只读令牌，见下文「任务只读令牌」。开发由模型在准备好时调用 `create_pull_request`：控制面立即固定唯一一次工作树快照，只在项目策略配置了非空测试命令时在快照之后运行它；模型提供的已执行测试命令只写入 PR 说明。策略测试失败、超时或输出截断时，工具返回 `validation_failed` 和输出，模型可修改后再次调用；成功只发布调用时的树，测试生成文件不进入 PR，无改动则正常结束且不创建 PR。控制面验证 diff 位置、head 和 bot 分支归属并负责推送与开 PR，同一 Issue 复用同一 bot 分支和 PR，Review 只允许 COMMENT，不自动合并。

## 使用与权限

超级管理员登记 GitHub App（App ID、RSA 私钥）或机器人账号（Token），为入口保存签名凭据，控制面随后自动同步每个账号可见的仓库：GitHub App 列出全部安装及其仓库，机器人账号列出 `/user/repos`；启动时和每 10 分钟全量对账一次，`installation`／`installation_repositories` 投递在同一事务里即时更新，并随后触发一次全量同步。同步只记录“已安装”，不登记、不启用：超级管理员在仓库页点“启动”，选择模型（部署共享模型会同时授权给该仓库）和是否开启自动开发后，才登记仓库、创建虚拟电脑并开始检视；启动前收到的事件只归档，不补跑。已启用的仓库可以“禁用”：停止处理新事件、中止正在执行的任务并停止虚拟电脑，数据保留，之后可再启用。仓库只能经同步出现、再由超级管理员启动，没有手动登记入口。超级管理员可以“删除”项目，但只在仓库已删除、或当前账号已完全不能访问它时允许：已移出安装（公开仓库别人仍能匿名读取也算）、安装被暂停或已不存在，以及读取仓库得到 404 或 403。删除时当场向 GitHub 核对，不看列表上的旧状态；仍能访问（包括权限不足）、GitHub 不可用、凭据缺失或答复不确定时拒绝，记录保留。核对通过后先禁用项目并取消未结束的任务，再走现有的环境删除（去掉各代容器和网络，工作卷都保留，不执行 `docker volume rm`），等执行中的任务退出后，在一个事务里删掉只属于该项目的记录：策略、成员分配、专属模型及其价格和授权、外部客户端及其授权、订阅、轮询进度和转发、投递、看板数据、任务及其日志和用量、环境记录、接入状态以及各账号安装列表里的这一行；操作审计保留。之后安装同步再看到这个仓库，它会像新仓库一样出现。从未启动的仓库满足同样条件时，只去掉安装列表里的行。项目列表在仍能看到、但安装授予的权限低于所需（对照 App 所需权限；机器人账号对照写入角色）的仓库上标出“权限不足”，标题写明缺哪些权限、当前是什么；这种仓库不能删除。徽章用同步时读到的授予权限，打开列表时若已超过 10 分钟，后台重读一次并就地替换徽章，不随任务数刷新，也不重画列表。任务执行时校验账号、实际仓库 ID 和所有者；App 在控制面签发 JWT、取得目标仓库安装令牌，机器人账号使用已保存的 Token，均不进入项目环境。仓库 ID 使用字符串提交，避免 JavaScript 大整数丢精度。

超级管理员可创建用户和分配项目管理员。每名项目管理员可分配多个仓库，每个仓库可有多名项目管理员。授权分两种，可以同时存在并取并集：单个仓库（可以是已安装但尚未启用的仓库，启用后项目沿用安装 ID，授权随即生效）和整个组织（按 `owner_id`，覆盖该组织已经启用和以后启用的项目，但不会因此启用安装）。项目管理员只看到并操作自己的仓库、投递、模型、策略及任务读取接口；无筛选查询同样受限，未关联仓库或验签失败的投递仅超级管理员可见。账号凭据、全局用户和授权关系接口只允许超级管理员调用。用户停用会撤销已有会话，仓库分配调整和组织下新启用的项目在后续请求立即生效；不能停用最后一名超级管理员。超级管理员可以删除用户：会话立即失效，仓库和组织授权、个人看板设置一并删除，登录名可以重新使用，操作审计保留；不能删除最后一名活跃的超级管理员，删除自己也要求还有另一名活跃的超级管理员。超级管理员可以删除 GitHub App 或机器人账号，前提是没有项目还在使用它；删除只从本系统移除账号、它的 Webhook 入口、安装同步记录和封存的凭据，不在 GitHub 上卸载 App，也不删除任何仓库。

模型配置包含接口 URL、API Key、模型名。超级管理员可管理全部模型；项目管理员可为自己的仓库创建和更新模型。部署共享模型由超级管理员通过 `models/:id/projects` 指定可用仓库，项目管理员只能读配置状态、选用，不能修改共享模型。超级管理员在仓库策略或“启动”中选择共享模型时，会同时把它授权给该仓库。仓库策略保存选用的模型 ID。保存即信任，可以发送本项目代码、日志和测试材料，不增加数据授权等待状态。接口采用兼容 Chat Completions 的 JSON 工具调用协议；URL 按填写的路径使用：去掉末尾的 `/` 和末尾的 `/chat/completions` 得到基址，对话请求发往「基址 + `/chat/completions`」，模型列表取自「基址 + `/models`」；不会自动添加或删除 `/v1`。路由接在 URL 文本末尾，所以 URL 不能带查询串或 `#`，否则路由会落进其中。因此 `https://example.com/v1` 请求 `https://example.com/v1/chat/completions`，`https://example.com` 请求 `https://example.com/chat/completions`。多数兼容接口的基址以 `/v1` 结尾；基址不以 `/v1` 结尾时，添加模型的表单、接入向导和已保存的模型都会提示，但仍允许保存。供应商的新增／编辑表单统一提供「获取模型列表」（最多返回 200 个 id，超出时注明已截断），支持多选或手动添加模型，并对同一范围、同一请求地址下的模型批量更新 URL 或更换／撤销 Key；模型行保留单条「测试模型」（用固定的一句探测请求、`max_completion_tokens` 为 32 发送一次 Chat Completions）；二者 15 秒超时，只返回上游状态码和上游 JSON 错误字段里的简短说明，不回显其他响应正文，也不返回 Key，不创建任务、不读取仓库，权限与编辑该模型相同。没有模型配置、撤销 Key、认证失败会显示 waiting_configuration；网络／限流故障退避重试，持续故障停止任务。

账号凭据、入口签名材料和模型 Key 用 AES-256-GCM 加密，密文绑定记录 ID。读取和写入响应均只返回是否已配置，不返回明文或密文。更新时留空或仅空白的凭据保持原值；撤销使用专用动作，不能靠提交空字符串撤销。模型 PATCH 必须带读取到的 `version`，旧版本返回 409。撤销账号凭据不会连带撤销入口签名；要禁用入口需单独撤销该入口。

浏览器管理入口以项目为单位组织：“项目”页列出已安装和已登记的仓库及“未启动／工作中／已禁用／已移出安装”状态，超级管理员可同步安装列表、启动、启用或禁用；点每行的“设置”进入该项目独立的设置页（`#/projects/<仓库 ID>/<类别>`，可直接分享和刷新），左侧类别为基本设置（仓库信息、处理账号、基准分支）、机器配置（虚拟电脑状态、实时资源、软件安装与初始化结果、启停与重置，以及 CPU、内存、进程数、/tmp、外网、额外软件包、环境变量和初始化脚本）、任务总览（项目默认模型、六个内置任务的模型与实际规则、共享的检视／开发设置、行为指南、项目专属与部署共享模型，以及规则来源表和只读仓库 skill）、发版本、项目笔记、外部执行、成员（仅超级管理员，分配项目管理员）和运行记录（当前任务、最近任务与命令）。旧的 `/model`、`/review`、`/development`、`/rules` 项目地址规范到任务总览并定位相应区域。项目管理员只看到自己的项目，机器配置只读。看板卡片进入的任务详情按时间线展示 Agent 工作过程：工作区准备、每一步模型思考与工具选择、读写的文件、在项目容器中执行的命令及退出码和输出、GitHub 发布和故障；运行中每 2 秒刷新，正在执行的命令单独显示并实时追加输出。每个页面都有地址（如 `#/board`、`#/settings/users`），刷新后停在原页面；旧地址 `#/reviews`、`#/developments` 分别选择看板的检视、开发类别。账号和用户在「全局设置」的对应类别里新增，凭据轮换等其余管理操作通过[管理 API](api.md) 完成。

## 工作看板

「看板」按 `(repository_id,object_type,object_number,card_category)` 标识一类工作。检视和开发各投影一张卡，即使另一类任务更新更晚，也不会改变当前卡片的状态或点击范围；尚无任务的 GitHub 对象保留未开始的检视卡。bot 发布的 PR 与来源 Issue 保持分离。发版本使用 `project_releases` 的现有记录，以 `release_id` 标识。默认显示全部对象，也可筛 Issue 或 PR；PR 开发的徽章显示「跟进」。筛选与分列分区呈现，分列支持 bot 执行阶段、仓库、执行状态、类别和自定义字段；明确筛掉的仓库或类别不生成列，零数量状态用紧凑计数表示。桌面锁定视口、列内纵向滚动；窄屏通过当前分组下拉显示一组纵向卡片。每 15 秒静默刷新第一页，拖动、输入或打开弹窗时跳过。卡片标题查询自身类别的关联任务，只有一个时直接进入任务详情，多个时在同一个弹窗内选择；执行状态筛选不隐藏该类别的历史任务。发版本进入项目现有发版记录，GitHub 外链直接打开 GitHub。

`board_objects` 是本地摘要表，由 `tasks` 与已验证、完整、非重复的 `deliveries` 在写入事务内通过触发器更新；包含评论里的 PR、检查和工作流事件引用的 PR 列表，以及开发任务结果中的新 PR 编号。首次升级按 rowid 每批 250 行回填历史。标题、GitHub 打开／关闭状态和草稿标记各自保留最近已知值，缺省字段不会抹掉之前的元数据。看板不扫描 GitHub，也不在绘制时按卡片请求 GitHub；对象与发版本的混合查询只取摘要、最新任务和发布阶段的必要列，每页最多 100 张，不返回发版本原始 `data`。对象、最近更新时间及任务对象关联均有索引；两类卡片都先应用仓库授权，空筛选不会扩展项目管理员的权限。

bot 执行阶段沿用未检视、正在检视、已检视、正在开发、已开发、需要处理六个阶段；混合对象时开发阶段文案同时涵盖跟进和发版。每一类任务单独按 `updated_at`（空值回退 `created_at`）取最近记录，独立计算该卡的阶段和执行状态。执行状态为正在执行、排队、失败、已完成、等待处理和其他／未开始，取消和过时任务不算正在执行、排队或失败。默认排除已关闭对象，可显式包含；草稿 PR 保留标记。查询返回全量筛选结果的 `work_count` 与 `column_counts`，列计数不受当前已加载页数影响；`counts` 则表示去重的 Issue／PR 对象数量，忽略对象类型筛选但保留其他条件。

`board_views` 按用户保存分列、筛选（包括对象类型）和折叠列（`hidden_columns`）。全部对象可用无对象筛选或 `object_type:all` 表示；不再使用浏览器中另存的对象类型覆盖视图。旧地址只在进入时设置类别，随即替换为 `#/board`，不能覆盖后来选择或另存的视图。内置默认看板可保存标准维度，不能删除、改名或增加阶段。自定义单选字段、选项和对象值仍分别存于 `board_fields`、`board_options`、`board_values`，按用户隔离；同一 GitHub 对象的工作卡共享个人字段值。只有自定义字段允许拖动与选择框修改值，执行阶段没有写接口，也不会因看板操作触发、停止或重试任务。

## 任务用量与成本

`task_metrics` 随任务状态进入和离开执行区间累计毫秒，运行中的时长在查询时动态补足；执行器定时保存计时检查点，排队与等待不计入。恢复上一个进程遗留的运行任务时关闭旧计时区间并标记不完整，避免把停机时间算成执行。重试保留累计值。升级前没有可靠计时的历史任务明确标记不完整，任务删除时附属计时级联删除。

模型调用只在控制面代理中记账：发起 HTTP 请求前插入 `model_requests`，收到响应后先保存用量，再将响应交给 runner。一次实际请求只有一条记录；同一回复尚未被 runner 取走时的重复轮询不会重记，实际发出的重试请求单独计数，runner 交付失败也不会抹掉已经发生的用量。连接异常、服务错误、缺少 usage 等保留为未知记录。兼容标准 Chat Completions 的 `prompt_tokens_details.cached_tokens` 与 DeepSeek 的 `prompt_cache_hit_tokens`，同时接受 `input_tokens/output_tokens` 形式。缓存命中 token 是输入子集；命中率按累计 token 加权，缺少数据不当作零命中。字段口径见 [Chat Completions 对象](https://platform.openai.com/docs/api-reference/chat/object) 和 [DeepSeek Chat Completions](https://api-docs.deepseek.com/api/create-chat-completion/)。

`model_pricing` 按模型保存美元或人民币的每百万输入／输出／缓存命中单价。请求账本保存当时的模型名、币种、单价快照和估算费用，不保存密钥或请求／响应全文；改价不重算历史。输入费用先扣除缓存命中部分，再分别按输入价和缓存价计算。未配置价格或缺少必要 token 时费用未知，不伪造免费请求；币种分别汇总，不作汇率换算。任务删除后账本仅解除任务关联，保留项目费用。共享模型价格沿用超级管理员编辑边界。

`GET /api/costs` 接收浏览器 IANA 时区，在用户授权仓库和限定本地日期区间内按 `requested_at` 的本地日、项目聚合费用和 token。使用带边界余量的日期与仓库／日期索引过滤，再按该时区的历史偏移和夏令时规则精确筛选与分桶；默认最近 30 天，最多 366 天及 5000 个费用分组。四类控制面任务独立聚合，不放大费用分组配额；数量和整段累计执行耗时都归入 `created_at` 的本地日，不按执行区间拆分。创建日期缺失时单独列为日期不明，不进入每日或范围总数；缺失耗时保留 null 和不完整计数。统计页同时展示 token、任务数量及耗时，并保留按项目着色的每日堆叠费用柱状图、可聚焦色块的当日金额和占比、项目汇总及每日明细。金额与占比只针对已计价记录，未知请求单独提示，历史未记录的数据不推算。这里只覆盖经控制面代理的模型费用，不包含外部执行端自行调用的模型或项目容器内其他服务的费用。

## 项目环境生命周期

新增仓库默认启用，后台登记一个环境；创建与周期对账均按仓库 ID 幂等，不随 Issue 或 PR 结束而删除。启动和后续命令复用同一容器及卷。每个仓库仍只有一台虚拟电脑，不为单个任务另开容器，但一台电脑可以同时运行多个任务（并发度见「检视与开发数据流」）：manager 让同一仓库最多 N 个执行请求并行，N 由控制面按项目并发度下发，调低时不少于正在运行的任务数；启动、停止、重置、删除和配置独占这台电脑，与执行请求按到达顺序排队，不会被持续到来的执行请求饿死。电脑上有执行请求时状态为 busy，busy 本身不拒绝新的执行请求；不同仓库可并行。CPU、内存、进程数和 /tmp 仍是这台电脑的一份限额，由同时运行的任务共用，不随并发度放大。项目没有自己设置的资源跟随 manager 保存的全局默认值（超级管理员在全局设置里修改，内置为 2 CPU、4096 MiB、1024 个进程、1024 MiB /tmp）；manager 记下当前容器创建时用的资源，默认值改变后在详情里报告 `resources_pending`，控制面对账时只在这台电脑没有任务认领、也没有其他待完成操作时记下一次 refresh 操作，engine 在它完成前不在这台电脑上领取新任务，manager 收到 refresh 后按当前规格重建不一致的容器，工作卷和代次不变。升级到可配置默认值时，manager 和控制面各把已保存规格里等于内置默认值的资源删除一次，让这些项目跟随全局默认。命令结束后容器继续运行，不再重启：默认清理命令的进程组，再由 runner 结束这个任务残留的进程（另建会话的守护进程也会被结束），其他任务的进程不受影响。runner 按进程环境里的 `BOT_WORKSPACE_ID` 标记、发起它的 runner 请求或 agent、所在的任务目录或父进程判断进程属于哪个任务。任务结束时结束自己的全部进程；电脑上最后一个结束的任务再清理除 init、空闲进程和 runner 以外的所有残留进程（几个任务同时结束时，已进入收尾的任务不算在内，所以其中最后一个仍会清理），清理期间控制面不在这台电脑上启动新任务；清理失败时才回退为重启容器。这次重启在项目锁内独占进行：先等正在执行的请求结束，之后到达的请求排在它后面，所以没有请求会在容器被换掉的中途执行；重启结束了电脑上各任务的进程，这些任务重新开始一次尝试，电脑保持就绪，工作卷和代次不变。某个任务的执行请求失败时，只结束该任务的进程，电脑和其他任务继续运行，连这一步也失败才停止整台电脑。命令可声明 `keep_background`，这时它启动的后台进程保留给同一任务后续的命令使用，任务结束时统一结束，其他任务的命令不会结束它们。容器以 Docker init 运行以回收僵尸进程；批准镜像、init 或网络策略变化后，下次 provision 时原地重建容器，卷和 generation 不变。

停止会将仓库 enabled 设为 false，停容器并保留卷；再次启动复用原代次和数据。签名可信的 App 卸载／暂停事件按账号和所有者范围停用，移除仓库事件按账号和仓库 ID 停用；这些意图随投递事务保存，再由后台停止环境，不在 webhook 响应链路调用 Docker。全量同步发现仓库不再安装时只标记“已移出安装”，不自动改变启用状态。停止、重置或删除会先中断这台电脑上所有正在执行的长命令。

重置先停止所有旧代容器并确认不再运行，然后增加 generation、保存旧卷，创建新代容器、新卷和新网络。失败进入 reset_failed，禁止普通启动旧环境，必须显式重试重置。删除虚拟电脑只删除受管容器和网络，保留工作卷和笔记卷；停用和卸载不会删除资源。旧代容器始终停止，旧卷仅保留待备份／清理，不挂到新项目环境。

manager 重启会先停止不确定的执行，标记未完成操作 interrupted，再用同一代容器和卷检查 runner／journal 后恢复 ready；重置中断则保持 reset_failed。运行期发现容器重启或退出同样重新恢复，不以 Docker running 代替 ready：空闲电脑由周期检查恢复；执行请求发现容器已被 manager 以外的原因重启或停止时，这个请求失败（`recovery_required`），电脑按上面的方式独占重启，不再整台停下并标记失败。已启用项目的电脑处于 failed 时，控制面对账会自动再启动它，两次尝试之间从 30 秒起每次翻倍、最长 30 分钟，启动成功后重新计时；重置失败（reset_failed）仍需人工重置。操作 ID 持久化去重，代次检查阻止旧请求写新环境，状态 revision 防止旧响应覆盖新状态。控制面保存操作意图并以原 ID 重试丢失响应，不自动重复重置。

当前 runner 为无网络监听的一次性固定执行入口：manager 通过 Docker exec 发送校验后的请求，返回 JSON 与持久 journal，调用者不能指定 exec argv 或用户。支持工作区相对文件读取／写入和 shell 命令，命令不限时长，运行到结束为止；要中断正在执行的命令，在机器配置中停止或重置虚拟电脑；单次写入 48 KiB、读取 1 MiB、命令输出 1 MiB。命令运行中输出同步写入 journal 旁的临时文件，manager 的只读 `output` 接口按字节偏移读取，不占用项目锁；命令完成后该文件删除，完整结果保存在 journal。journal 每次调用一条记录，只在调用后不久有用（重复的操作 ID 取回首次结果、读取刚结束命令的输出），所以 manager 在每次 provision 后和运行中每 6 小时在后台、不占项目锁地清理一次：删除超过 1 天的记录，仍记为运行中的命令和它的输出保留 7 天。runner 的健康检查不读 journal，记录再多也不拖慢启动。项目运行用户为 10001，根文件系统只读，工作卷可写，CPU、内存、进程数和 /tmp 默认为 2 核、4096 MB、1024、1024 MB，超级管理员可按仓库在 manager 允许的范围内修改。批准的项目镜像自带 Node.js 22（npm、corepack 的 pnpm／yarn）、Python 3.11（pip、venv、uv）、gcc／g++／make、git、git-lfs、curl、wget、jq、ripgrep、sqlite3、zip／unzip，镜像自带包清单在 `/opt/bot/image-packages`。仓库需要的系统软件包由 manager 以批准镜像为底、用固定的 apt 命令构建派生镜像（按底层镜像和包集合缓存，root 只出现在构建阶段）；非机密环境变量注入容器并传给每条命令；初始化脚本以项目用户在 `/workspace` 运行，`HOME=/workspace/home` 在工作卷中，`~/.local/bin`、`~/.cargo/bin`、`~/.npm-global/bin` 在 PATH 上，脚本或代次变化时重新运行，结果和输出在虚拟电脑页可见。Git 操作在容器内执行。任务工具支持隔离工作目录、分块文件与 Git 候选；上游 API 认证始终由控制面代理。执行入口仅供内部控制面和验收调用，管理页面没有通用终端。

每个仓库的独立稳定笔记卷读写挂在 `/workspace/project-notes`，任务通过 `../notes/` 使用；停机、重建、禁用和重置代次后保留，删除项目时随环境删除笔记卷，旧工作卷仍保留。项目页由 manager 直接读写同一份卷内文件，电脑未启动时也能编辑，无需启动项目或辅助容器。

## 检视与开发数据流

在仓库 policy 中选择 `model_id`，打开 `review_enabled`，需要自动实现时再打开 `development_enabled`，建议设置可信的 `test_command`。Issue 在 opened 时检视一次；PR 在 opened、ready_for_review、synchronize 且非草稿时检视当前 head。这三类触发可在项目「任务总览」的检视组分别关闭（关闭 PR 新提交触发后，bot PR 的自动跟进也随之停止）。

打开后的更新也会再检视一次，两个开关默认打开：「Issue 的标题或正文被修改、有新评论后」对应 `issues.edited`（`changes` 含 title 或 body）和 `issue_comment.created`；「PR 的标题或描述被修改、有新评论、提交检视或回复检视意见后」对应 `pull_request.edited`、PR 对话里的 `issue_comment.created`、`pull_request_review_comment.created`，以及有正文或要求修改的 `pull_request_review.submitted`（GitHub 给每条行内回复包的无正文 review 由对应的评论事件处理）。Issue 更新还要求 Issue 检视开启，PR 讨论还要求 PR 检视开启；草稿、已关闭对象和 bot 自己写的内容不触发。评论、行内回复和提交的检视只在发言人是对象作者，或 `author_association` 为 `OWNER`、`MEMBER`、`COLLABORATOR` 时触发，公开仓库里的其他人发言不会消耗模型额度；修改标题或正文在 GitHub 上本来就只有作者和有仓库权限的人能做。机器人账号以普通用户身份发言，所以按正文里的 `<!-- dept-bot` 标记识别，App 发言另按 `sender.type=Bot` 识别；bot 账号修改自己创建的 PR 描述也不触发。同一仓库、同一检视类型（`review.issue`／`review.pr`）、同一编号上的更新进入当前检视。尚未发出第一次模型请求时，包括排队、重试等待、等待配置／环境和准备阶段，触发记录全部并入，不设 20 条截断；开始前重新读取 GitHub 当前标题、完整正文和全部讨论。模型已经开始时，不取消任务，不增加另一条任务，也不打断当前模型 HTTP 请求或工具调用。Pi 在每一回合的工具结果写入历史后，通过控制面邮箱检查持久更新收件箱；控制面同时刷新 `../context/` 的对象与讨论文件，再按投递顺序补入用户消息，包含操作者、改动内容和新正文。模型和工具调用费用仍记在当前任务上。并发度大于 1、同一对象存在多条执行中的检视时，选择最近认领开始的那条，不取消其他检视。每次更新按 `repositoryId:kind:number:update:<投递记录>` 去重。任务上下文带 `trigger`（原因、操作者、改动前的标题或正文、评论或检视链接），评论类触发同时带 `trigger_comment`；模型先回应这次更新，再对照当前状态核对之前的发现，不重复已解决的问题。PR 的更新检视和提到触发一样：head 已变化时直接作废，不另排 head 检视，也不启动 bot PR 的自动修订。未启用检视的仓库只归档，草稿不建检视任务。投递去重和任务逻辑去重独立；归档、去重与入队在同一事务提交后才确认成功。

打开的 Issue 或 PR 对话中新发布的评论（`issue_comment.created`）提到配置名字时，触发一次检视或补入当前检视。`BOT_MENTION_NAMES` 未设置时为 `bot,agent-ci-infra-bot`；设置后按逗号分隔替换默认名字，忽略大小写和名字两侧空白，整个值为 `off` 时关闭评论触发。匹配纯文本 `@名字`，无需该 GitHub 账号存在或属于本部署，也不查询用户接口；`@` 前须为开头或非字母数字，名字后不能紧跟字母、数字或连字符，因此 `@bot-extra` 不匹配 `bot`。提到名字的评论不受上面的更新开关限制，但和普通更新一样：开始前并入、开始后在回合之间补用户消息；没有可合并的检视才新建任务。Bot 发送的评论、评论的编辑、删除和重新打开不按提到触发（不提到名字的新评论按上面的更新规则处理）。评论遵守 Issue／PR 的检视开关，PR 评论读取当前 head，草稿或已关闭对象不入队。每条评论按 `repositoryId:kind:number:comment:commentId` 去重，PR 的 `head_sha` 仍为当前 40 位 SHA；不同评论可以再次检视同一 head，原有 opened／head 去重键不变。任务保留触发评论的 ID、正文和链接，并把它作为 `trigger_comment` 交给检视上下文。

检视恢复的只是消息历史：从控制面 `review_sessions` 表读取同一对象最近一次状态为 `succeeded` 的会话，不读取登录用的 `sessions`。失败、取消、`superseded` 和仍在执行的会话都不能成为来源；自动重试和手动重试使用空会话，并在第一次模型请求前重读最新讨论。系统提示、规则、skills、工具、检出和 `../notes/` 每次按当前任务加载；延续的第一条内容写明当前 head，并提醒历史代码结论可能属于旧版本。会话不依赖容器内存或任务目录，容器重建与三天任务目录清理不会删除控制面会话；对象关闭后再保留 15 天，期间重开可延续，超过期限重开从空会话开始，项目删除时一并删除。工作区仅为检出缓存：目录存在、提交相同、代次匹配且检出干净时才复用，仍按三天无活动清理。项目笔记独立保留、只向前更新；开发任务不加载检视会话，也不接收检视更新。

Pi 启用会话压缩，控制面保存压缩后的消息投影，不恢复旧系统提示或工具配置。历史通过分块邮箱传输，检查点至多 32 MiB；发往模型的单次请求仍须同时满足 2 MiB 和 128k 上下文上限（包含输出预留），压缩费用记在本次任务。压缩后仍超限则本次失败，重试丢弃这次历史，使用空会话。

`finish_review` 暂存当前结果，Pi 保持可继续状态。在 GitHub 第一次写入之前，控制面重新检查更新收件箱；若有新更新，则补回同一会话，允许模型再次调用 `finish_review`，只发布最后一版。一旦总结评论、行内 review 或标签的第一次写入发出，后续更新留给下一条任务；下一条等待当前发布完成后才开始，并延续当前成功会话。当前写入按原 outbox 契约完成，不因讨论更新而取消。PR 新提交仍沿用 `validate()`：旧任务在校验发现 head 改变时标为 `superseded`（`pull_request_head_changed`），另检视新 SHA，不向旧工作区补入 head 变化；新检视只延续上次成功历史。关闭、转为草稿以及 bot 自己的评论的处理保持原约定。

新建 App 的 manifest 订阅 `issues`、`pull_request`、`issue_comment`、`pull_request_review`、`pull_request_review_comment`，不包含由 GitHub 自动投递的 `installation` 或 `installation_repositories`。已创建的 App 不会随代码更新自动新增订阅：App 所有者需要在 GitHub App 的 Permissions & events 设置中勾选 **Issue comment**、**Pull request review**、**Pull request review comment** 并保存；用令牌登记仓库 webhook 的部署也需要把这三个事件加入订阅。

后台按项目并发度认领任务。全局设置给出默认并发度，未设置时为 1，所以不改设置时同一仓库仍一次只运行一个任务；项目可以在「机器配置」里覆盖，留空时用全局默认，两者都是 1–32 的整数，项目值就是这台电脑同时运行的任务数。超级管理员在「全局设置」改默认值；项目管理员只能改自己项目的覆盖值，不能读写全局设置。超出并发度的任务按创建顺序继续排队，不会因此失败。每个任务持有自己的认领（`task_claims`），检查点只核对本任务的认领，并使用自己的 `/workspace/tasks/<workspace_id>`；文件工具和 runner 写入只落在本任务目录内，越界路径和指向目录外的符号链接被拒绝，各任务的命令都从自己的仓库目录开始运行。命令仍以同一项目用户运行，共用 `HOME=/workspace/home`。停止、重置、代次变化和禁用项目仍会中止这台电脑上所有进行中的任务；修改电脑配置会重建容器，正在运行的任务被中断后重新准备。任务拉取本仓 Issue／PR、讨论、完整分页 diff 与固定 SHA 的代码材料。已保存模型只收到这个项目的上下文，并可调用 read_file、write_file、run_command 等受任务约束的工具。仓库材料属于不可信输入，不能修改权限、镜像、发布目标或认证。单个任务不限模型调用次数，也没有总时长上限，禁用项目或停止虚拟电脑可以中止正在执行的任务；模型调用 run_command 时命令不限时长，可选 `timeout_seconds` 为可能卡住的命令自设超时，服务和监视进程用 `keep_background` 放到后台；仓库测试验证同样不限时长；任务上下文包含虚拟电脑的资源、工具链、额外软件包和环境变量名；临时调用失败最多重试 5 次，配置故障单独显示。

每次检视发布一条总结讨论评论，包含总结、非行内 finding 和检视 SHA。Issue 只用普通评论。PR 每条 finding 由模型选择普通评论或行内评论并给出理由，服务端用真实 diff 校验 path／line／side；缺少可核对位置时转普通评论，不猜行号。行内 Review 的 event 恒为 COMMENT，模型不能选择批准或请求变更，没有自动合并接口。发布前重新检查 head，过时任务标为 superseded；评论写明实际检视 SHA，Review 和每条行内评论的 GitHub ID 保存到任务回执。标签都在总结评论发布成功后由控制面用同一安装令牌一次加上，重复执行不会重复添加：

- `labels.md` 声明了 `review_label` 时，加上这个检视标签；仓库没有该标签时由 GitHub 创建。
- 检视任务准备时，控制面读取仓库现有标签，作为 `repository_labels` 交给模型。模型在 `finish_review` 的 `labels` 里选分类标签。控制面只加仓库已有、不属于保留标签、而且 Issue／PR 上该维度（`type/`、`priority/` 等前缀）还没有值的那些；`priority` 只取第一个，最多 8 个。保留标签包括检视标签、开发标签、`agent/*`、`blocker`、`priority/critical`、`pr/*`、`gate/*`。

模型不调用标签接口，也不能让 GitHub 新建标签。

Issue 检视结果明确要求代码变更、存在原文证据且无需补充信息时，若仓库打开开发，并且有人（不是 App）在该 Issue 上加了开发标签（`.bot/rules/issue-development.md` 第一行 `development_label:`，默认 `bot-develop`）、Issue 没有指派人，创建关联开发任务。标签可以在检视前或检视后加：检视发布时已满足就立即创建，否则由之后的 `issues.labeled` 事件创建；发布前再次确认标签仍在、仍无指派人。在同一项目容器的新任务工作目录中修改代码，模型完成后服务端再次运行仓库指定测试；未配置固定测试时使用模型给出的测试命令，不能没有测试。失败不会推分支或开 PR。成功后检查测试前后候选 tree 一致，再由控制面发布唯一 `bot/issue-...` 分支，并创建 PR、回填链接。默认分支从 GitHub 元数据或仓库 policy 获取，不写死。

评论触发的 Issue 检视也必须先成功发布评论，再通过上述开发授权检查；webhook 不直接创建开发任务。同一 Issue 已有排队、重试、等待配置／环境／权限／PR head／发布或执行中的 `development.issue` 时，不再创建第二条开发任务。PR 对话里的 `@` 只再次检视当前 head，包括 bot 自己创建的 PR，也不会启动开发或推送提交；入队后 head 变化时，这条评论检视标为 superseded，不衍生普通 head 检视任务。

别人的 PR 只检视，不产生向作者分支提交的任务；分支名或机器人名称不能代替归属记录。由本系统创建的 PR 保存不可变 PR ID、作者、head 仓库、分支和发布 SHA，只有这些身份仍匹配、策略允许且确有修改项时才在原分支跟进。跟进默认最多 3 轮，可在 policy 的 max_revisions 中设置 0–10；Issue 的再次检视要继续推进这个 Issue 已有的 bot PR 时也计入同一预算，用完后不再自动开发。不另开 PR，不强推，不自动合并。

## 任务只读令牌

模型调用 `github_read_token` 时，runner 在任务邮箱写入请求，控制面轮询到后为本仓库签发一个 GitHub App 安装令牌：`repository_ids` 只含当前仓库，权限只取 `metadata`、`contents`、`issues`、`pull_requests`、`actions`、`checks`、`statuses` 中安装已授予的项，并一律降为 read；签发结果里只要有任何一项不是 read 就拒绝。机器人账号只有一个能写的长期 Token，不能派生更窄的令牌，所以不提供只读令牌，模型会收到 `github_app_required`。

令牌经 manager 直接交给 runner，不写入 `task_tools` 或任务日志；runner 只把它放进该任务之后的 `run_command` 环境变量 `GH_TOKEN`、`GITHUB_TOKEN`，并在命令输出中替换为 `[REDACTED]`。模型拿到的工具结果只有变量名、仓库、权限和到期时间，看不到令牌本身。令牌加入任务的脱敏表，发往模型服务商的请求也会先脱敏。同一任务最多签发 10 次；模型阶段结束（完成、失败或被中止）时，控制面逐个调用 `DELETE /installation/token` 撤销。

令牌和 PR 检视时运行的仓库测试处在同一台虚拟电脑里，测试代码能读到这些环境变量，所以令牌被设计成只读、只覆盖本仓库，并在模型阶段结束时撤销；GitHub 安装令牌最长有效一小时。评论、标签、行内检视、分支和 PR 仍只由控制面用自己的令牌发布。读取 Actions 和检查状态需要 App 授予 Actions、Checks、Commit statuses 权限；接入向导生成的 manifest 申请 Actions、Checks、Commit statuses 写（写权限留给控制面发布 commit status、检查结果和重跑 CI；任务令牌仍一律降为读）。之前创建的 App 需要在 GitHub 上补加这三项权限，并由安装方同意。检视和开发的令牌刻意不申请 workflows：开发任务改到 `.github/workflows/` 时 GitHub 会拒绝发布。App 本身可以为一键接入获得 Workflows，但它只出现在接入专用的令牌里（见下文「一键接入」），检视、开发和只读令牌都不申请。也不申请 administration、secrets、security_events、vulnerability_alerts、secret_scanning_alerts：任务令牌对 PR 代码可见，不能让它读到仓库设置、密钥或未公开的漏洞告警。

## 一键接入与公共看板托管

仓库列表直接提供「看板」开关，与检视、开发开关并列；无需启动项目。公开仓默认开启，私有仓默认关闭。超管可以为任意已安装仓库保存开启或关闭状态，开关同时控制单仓页面与公共 Dashboard 汇总。关闭后立即停止对外提供旧快照，webhook 和后台采集也不能重新开启它。「公共配置」仅保留原门禁 PR 流程，不再包含单仓看板或 Dashboard 登记执行项。

公共 Dashboard 位于已验证的 webhook 公网地址 `/dashboard/`，单仓看板位于 `/boards/<owner>/<repo>/`（小写），看板目录位于 `/boards/`。三者只由 webhook 监听端口 8791 提供，不需要控制台登录；管理端口 8792 保留原控制台和其「看板」页面，不提供这些公开路径。公共地址沿用安装向导验证的 `onboarding.public.origin`。

开关设置保存在 `public_board_settings`，按仓库持久化，不随安装同步或重启重置。已有明确启用的私有仓授权迁移为开启，已经保存的关闭状态不会被旧授权重新打开。未保存选择的仓库在可见性变化后按新可见性使用默认值；已经保存的开或关保持不变，直到管理员再次拨动。开启私有仓会使其看板数据无需登录即可访问。卸载或删除后，公开路由立即排除该仓。门禁 PR 不改变开关设置。

验签通过且未重复的 webhook 在同一数据库事务中递增该仓的采集代数，包括已安装但未启动的仓库。后台持久队列合并投递、按仓采集、失败退避重试；新投递在采集过程中到达会保留为下一代任务。启动时补齐公开仓初始采集，重启后继续未完成的代数。采集失败保留上一份有效快照，新快照校验仓库身份后整体切换。所有公开请求重新核对安装状态和私有仓授权，内部 checkpoint、源码及凭据没有公开路由。

现有 Dashboard React 页面、单仓静态页面、社区统计采集器和增量采集器随 bot 一起构建。页面字段、统计方法和版式沿用原实现；门禁页取消未安装仓的设计占位回退，仅显示真实采集数据。Python 采集器只用标准库。快照、历史与内部增量状态保存在数据库旁的 `public-boards/` 数据目录，容器镜像包含 Python 3 和时区数据。`BOT_DASHBOARD_REPO` 与 GitHub Pages 不再参与托管或接入。

| 操作 | 目标 | 权限 |
| --- | --- | --- |
| 门禁 PR | 源仓 | contents 写、pull_requests 写、workflows 写、metadata 读 |
| 看板采集 | 源仓 | contents、issues、pull_requests、actions、metadata 只读，按安装实际授权裁剪 |
| 看板开关 | bot 本地 | 控制台超管；不向 GitHub 写配置 |

每次采集使用源仓自己的只读安装令牌并在结束时撤销，不再需要外部 dashboard 的 App 安装或 `PRIVATE_SOURCE_TOKEN`。CI-workflow 模板读取规则和门禁 PR 的权限边界保持原样。

## 代码快照与发布

控制面在自己的数据卷上为每个已启用仓库保留一份 bare mirror（`/data/git-cache/<仓库 ID>.git`，`BOT_GIT_CACHE_DIR` 可改位置），任务不必每次从 GitHub 重新下载整个仓库。任务准备时先把镜像更新到这次要检视或开发的提交，PR 任务还包括读取规则的默认分支提交：镜像里已有这些提交就不访问 GitHub；缺少时按 SHA `git fetch` 这些提交，GitHub 不按 SHA 提供时改取对应的 PR head 或分支 ref，而不是只更新默认分支。同一镜像的更新逐个进行；拉到的每个提交固定在 `refs/bot/commits/<sha>` 下，后续更新和维护不会删掉。安装令牌只作为一次性 HTTP 头经这次 fetch 的进程环境传给 git，只对 GitHub 返回的 clone 地址所在源生效，不写进 remote URL、镜像配置、FETCH_HEAD 或日志，也不进入项目容器；`github_read_token` 仍是只读，语义不变。规则文件随后从镜像在固定提交上读取。工作区优先是一个 git worktree：每台项目电脑在工作卷里有一份自己的 git 对象库（`/workspace/git/repo.git`），控制面先问它已有哪些提交（`git_have`），再从镜像打一个只含缺少部分的 pack（`git pack-objects --revs`，第一次是整个历史，之后通常只有新提交），按约 45 KB 分块直接传给电脑（`git_pack`，不写入任务记录），电脑用 `git index-pack` 校验并收下，把提交固定在 `refs/bot/commits/<sha>` 下（`git_import`）；然后为任务 `git worktree add --detach` 一个自己的工作目录并核对 tree（`workspace_checkout`）。PR 任务同时带上 PR 的 base 提交，agent 能用 `git diff <base>...<head>`、`git log` 自己查看改动；工作区里没有 remote 和凭据，令牌不进电脑。文件不再经控制面逐个复制，控制面改为在镜像里用 `git grep` 检查文件是否含有本任务的凭据，含有时任务停下（`credential_in_repository`）。子模块条目留在 tree 里但不检出，开发结果也不把它当作文件。超过 3 天没有活动的任务目录在电脑的定期清理里删除，并清理 worktree 登记、按需整理对象库。镜像不可用（fetch 失败、仓库没有 clone 地址、拉取后读不出等）、电脑上的这条路走不通时，回到下面原来的方式：从镜像或 Git 数据 API 逐个读取文件，按文件经 manager 以约 30 KB 分块写进任务自己的新工作目录，再构建只有这一个提交的本地 Git 快照，任务不会因此失败，日志写明原因。文件数超过 2000、单文件超过 1 MiB、合计超过 32 MiB 都不再使准备失败；递归 tree 被截断时丢弃不完整列表，改为逐目录非递归列举。子模块不克隆，子模块和不支持的 Git mode 不下载，日志记录路径和 mode；回到 Git 数据 API 读取时，[GitHub blob API](https://docs.github.com/en/rest/git/blobs#get-a-blob) 支持约 100 MB 以内的 blob，接口明确因文件过大拒绝返回时记录路径、大小和 HTTP 状态并跳过，coverage 列出跳过数量。权限错误、限流和普通 HTTP 错误仍按原有故障处理。跳过条目保留在上游，发布时沿用源 tree 并校验合并后的完整 tree，避免误删。复制方式下控制面一次只处理一个文件的内容，快照 blob 下载不受普通 GitHub 响应的 48 MiB 限制；二进制和符号链接按 Git 对象处理，相对文件工具不跟随越界符号链接；哈希不一致、路径越界和工作区被替换仍然失败，说明包含路径、期望与实际 SHA 或具体原因。

agent 拿到的是索引而不是全文：系统提示只含 `.bot/` 下的行为指南和规则；用户提示里是对象摘要（编号、标题、状态、作者、标签、正文前 1000 字）、PR 的 base 和 head（ref 与 SHA，以及查看改动的 git 命令）、上下文文件清单和 skill 索引（名称、用途、路径）。完整内容写在工作目录旁的 `../context/` 下，agent 需要时用 `read_file` 或命令读取：`object.json`（GitHub 返回的 Issue 或 PR）、`comments.json`（全部讨论评论），PR 另有 `files.json`（改动文件及 GitHub 的 patch）、`reviews.json`（全部 review）和 `review_comments.json`（全部行内评论），以及 `skills/<名称>/SKILL.md`（各 skill 全文）。这些文件经脱敏后直接写进电脑，不写入任务记录；skill 和规则都取自默认分支，工作目录里 PR 自带的 `.bot/` 和 `.agents/skills/` 只是被检视的内容。

GitHub 按发出请求的身份分别限制每小时请求数：GitHub App 的每个安装（一个组织或用户）一份，其中所有仓库和任务 agent 共用；Token 账号按 Token 所属的 GitHub 用户一份，这个用户的所有 Token 共用；App 自身的 JWT 请求另算，它的额度取自这些请求响应里的 `x-ratelimit-*` 头（`GET /rate_limit` 不接受 JWT），所以 App 发过请求之后才列出。控制面从每次 GitHub 响应的 `x-ratelimit-*` 头记下所属窗口的额度、剩余和重置时间，安装同步每 10 分钟也经 `GET /rate_limit`（不消耗额度）读取一次；窗口用完或被 GitHub 拒绝（含次级限流）后，同一凭据的请求不再发送，任务以 `github_rate_limited` 等到窗口重置（或 GitHub 要求的时长）后几秒内再继续，这类等待不占自动重试次数。引擎自动轮询的等待（等电脑、等配置、等 PR head、无重置时间的限流）同一原因连续出现时，每次等待时长翻倍，分别封顶 5、30、5、15 分钟，换了原因或手动重试后重新计算。

任务入队和准备、Agent 执行、策略测试、GitHub 发布阶段开始时即写入任务日志，包含仓库、固定提交 SHA、检视或开发模式、实际测试命令或发布目标；同一次尝试内的阶段开始去重，策略测试按实际命令操作记录，没有策略命令时不写测试开始日志。准备过程中每写完 100 个文件记录已写入数量、字节数和刚写完的路径，每个跳过条目立即记录路径及原因，构建本地 Git 树前再记一条，结束时保留 `snapshot` 汇总，其中记录文件来源（`git_cache` 或 `github_api`）和镜像状态（已有 `hit`、本次拉取 `fetched`、不可用 `unavailable`），跳过说明过长时标明省略条数。Pi 保留模型决策和工具结果事件，并在工具执行前写入 `tool_start`（文件路径、命令或动作名，不含写入内容），经现有 poll 复制到 `task_logs`；runner 在事件落盘前屏蔽已兑换的令牌，控制面继续经 Redactor 脱敏。运行中和成功后、失败或 `waiting_*`、`retry_wait` 的详情均保留完整时间线，故障步骤和侧栏直接展示 fault `detail`，无需打开原始数据；相同故障码、状态和说明在自动重试时只记录一次，自动重试用尽转为失败时另记一条。`retry_wait` 的自动重试依次等待 5、15、45、135 秒（限流按 `Retry-After`），第 5 次仍失败转为失败。`src/agent/failures.ts` 把每个故障码归入一类原因并给出下一步，任务和日志接口在读取时附上 `error_cause`／`cause`，旧日志同样适用。GitHub 和模型请求失败写明方法与路径（或模型名与主机）、HTTP 状态、对方的简短说明，以及超时、DNS、连接重置、TLS 等网络原因；GitHub 5xx 附带 `X-GitHub-Request-Id`。日志截断保持合法 JSON，并保留故障说明。

开发候选由容器内 Git 生成，控制面保存候选 tree、文件清单、测试输出与本地提交映射，经 Git 数据 API 上传 blob/tree/commit。tree 只把改动、新增和删除的路径叠加在源快照的 tree 上（`base_tree`），不再每次列出整个仓库：大仓库的完整清单会让 GitHub 超过单个请求 10 秒的处理上限，每次重试都返回 502/504。路径在文件和目录之间转换，或 GitHub 算出的 tree 与候选不一致时，退回完整清单。只有 GitHub 返回 tree 与已验证候选完全一致，才创建或更新登记的 bot 分支。更新固定 force:false；未知或变化的分支 head 会阻止发布。容器里没有 GitHub remote 认证、私钥或模型 Key；控制面只对仓库镜像运行 git fetch、ls-tree 和 cat-file，不检出代码，也不运行仓库里的脚本或钩子，命令仍不在 bot 宿主机上执行。真实仓库访问仍需为 App／账号提供相应 Contents、Issues 和 Pull requests 权限。

评论、Review、分支和 PR 都有持久 outbox。请求结果未知时按任务 marker、head 和远端对象先对账（从未发出或确定被拒绝的请求不查找，直接在发送前校验一次任务对象）；未能确认就保持 waiting_publication，不盲目重复；人工重试视为确认，结果未知的写入先再对账一次，仍查不到才重新发送。分支已推送后，基础分支前进不再阻止创建对应 PR。控制面重启后恢复未完成阶段，已完成任务不重新入队；manager 中断的命令不当作通过，重新检查环境后在新 attempt 工作目录继续，旧目录保留。同代已完成工具通过原操作 ID 回放，generation 变化会阻止旧任务直接写入新环境。

## 仓库自动化规则

PR 门禁、标签规范和合并队列是仓库策略，不写进每个仓库的 GitHub Actions：`src/automation/` 提供规则引擎和内置模块（`label-lint`、`pr-status`、`gate`、`merge-queue`）。每个仓库用 `config/repositories/<owner>__<repo>.yml` 声明自己的标签轴、门禁、合并策略和 CI 阶段（仓库示例见 [Jianyu010__PPMA.yml](../config/repositories/Jianyu010__PPMA.yml)），policy 的 `automation` 字段仍可覆盖，默认 dry-run、默认不自动合并。webhook 落库时规划动作并写入 `automation_runs`，执行器接入 outbox 后再产生真实写入。配置 schema 与新增模块的步骤见 [自动化规则](automation.md)。

## 外部执行端

管理入口的「外部执行端」可登记逐仓库客户端、配置 Webhook 事件过滤与签名转发，并查看投递和临时授权记录。个人电脑登记公钥、用本机私钥签发两分钟内有效的证明，GitHub Actions 使用受信任 OIDC 身份；检视完成后向公开 `/external/token` 兑换限定仓库的 Bot 安装令牌，再以 Bot 身份回复结果。只有 GitHub App 能签发此类临时 GitHub 凭据，不分发长期账号 Token。超级管理员可在该页设置实际 HTTPS 兑换地址，未设置时使用接入向导已验证的公开地址；旧客户端保留 ID 和订阅，但须登记公钥后才能继续兑换。完整接入、重试、权限与撤销边界见 [外部执行端](external-executors.md)。

## 当前限制

回退到逐文件复制时，任务工作区不含上游历史；尚未接入子模块／LFS、按域名白名单的出口代理和长命令跨 manager 重启续跑（manager 重启会中断正在执行的命令）。命令输出由控制台每 2 秒轮询增量读取，不是推送。策略编辑和部分授权管理继续通过已有管理 API 完成。没有聊天、图形桌面、浏览器接管或远程桌面能力。
