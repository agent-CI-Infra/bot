## 运行中发现并修正的问题

真实运行开始于 `d6ffb38`，集成检查点恢复使用 `79dfc59`，后来升级到 `0786af3`，这些版本在 run 配置中可查。不是宣称全程使用最终提交且零人工介入：

1. 初期手动合入与后台轮询重叠，曾重复安排集成。新增仓库级短操作串行化、当前状态去重、过期轮询结果校验，并用专门并发测试复现和验证。
2. 真实 GitHub PR 的 `base.sha` 滞后于 main，曾让第二项重复集成/QA。改为直接读取默认分支 ref；验收实例在 QA 期间升级恢复，使用原数据库、候选与授权，无验收覆盖。最终没有继续这一循环。PR 元数据滞后的回归覆盖在完整引擎测试中。
3. 合入意图可查询和撤回；来源工作区、执行基线、PR 所有权 head 分别绑定，避免把旧观察当成新候选证据。

此外，本 PR 在开发中与 Bot main 的管理服务改动产生实际冲突，保留双方能力并对组合代码重新检查。未将整个开发流程串行化来回避冲突。

## 检查、队列与边界

本机曾在合入管理服务之前完成 804/804 单测、43 项管理面浏览器回归；首次全量检查发现遗漏的错误码分类，已修正。合并最新 main 后最终全量检查为 **824/824 测试通过、零跳过，44 项 Playwright 浏览器回归通过**；构建、类型检查及六个 GitHub 必需检查通过。最终仍以 PR #185 当前提交及 merge group 的必需检查为准。

真实 GitHub 队列验收使用本 PR #185：独立读取固定提交与 CI/实验原始证据进行 fresh QA，以操作人显式授权调用本实现的合入接口，记录 GitHub queue entry、base/combined SHA 和最终 `repository_evolved`。最终队列状态、检查与合入事实见 PR/issue 的验收评论；不把“已入列”当成“已合入”。此入口导入的是操作人创建的 PR，明确没有伪造一个 Bot Dev 执行过程。认证信息和原始私有会话不提交到仓库。

L3 配置不是并行执行或普通 PR 发布的前置条件。无队列仓库仍依赖其当前策略、本地验证/QA 和 GitHub 现有规则；没有远端检查明确记 `no_remote_checks`。外部参与者可在最终 API 请求期间更新分支，要求原子组合 CI 的仓库应启用其 GitHub 队列/规则。本期不建设 #184 的 L1–L5 工程接管。

首次真实入队在 2026-11-08 05:59 UTC 被 GitHub 以 `merge_conflict` 移出：仓库采用 REBASE，分支中解决过冲突的合并历史不能逐提交干净重放。框架记录 `merge_queue_removed` 并停止自动合入，没有伪报成功。操作人保留原提交 `20781b43`，将交付整理为最新 main 上的单个提交，重新运行必需检查和独立验收，再次入队。这是实际失败与人工处理，不能计为平台自主修复该历史冲突。
