# 接入指南：把一个代码仓交给部门 bot

这份文档面向**使用 bot 的仓库维护者**：从"我有一个代码仓"到"门禁、单仓看板、公共 Dashboard 都接好了"，全部流程和需要你亲手做的几步。

---

## 访问入口

| 入口 | 地址 | 用途 |
| --- | --- | --- |
| **管理面（控制台）** | https://agent-ci-infra-bot-admin.llmbots.co/ | 启动项目、跑一键接入、管理用户与仓库授权 |
| **公共 Dashboard** | <webhook 公网地址>/dashboard/ | 看所有已登记仓库的门禁与时延等指标 |
| **单仓看板** | `<webhook 公网地址>/boards/<owner>/<repo>/` | 单个仓库的看板，`<owner>/<repo>` 用小写 |
| **GitHub App 安装页** | https://github.com/apps/agent-ci-infra-bot/installations/new | 把 bot 安装到你的账号/组织 |

### 管理面怎么登录

1. 打开 https://agent-ci-infra-bot-admin.llmbots.co/ ；
2. 如果出现 Cloudflare Access 的验证页，先填**你的邮箱**，收邮件验证码完成验证（这一步是网关鉴权，不是 bot 账号）；
3. 进入控制台登录页后，用管理员分配的**用户名 + 密码**登录；
4. 首次部署时首页会显示「创建第一名超级管理员」，由部署者初始化，之后这里只提供登录。

登录后顶部导航里有「接入向导」和各个列表页；普通使用者通常是**项目管理员**，只看到分配给自己的仓库，超级管理员能看到全部。

> 忘记密码或需要账号，找超级管理员在「用户管理」里重置或新建；控制台的写操作需要登录会话，长时间无操作后会要求重新登录。

## 0. 开始之前

| 你的仓库需要 | 说明 |
| --- | --- |
| 已安装 GitHub App | 门禁接入只使用 App 安装令牌；挂在机器人账号上的仓库不能接入 |
| 至少有一个提交 | 空仓库没有可读的事实，先推送代码 |
| 不限语言 | Node、Python、Go、Rust、Java 等都可以；不要求 `package.json` 或 npm 锁文件 |
| 检查命令来自仓库自己 | agent 只按仓库里已有的脚本、Makefile、构建文件和 workflow 提议命令，不确定的会问你 |
| 是公开或私有仓库 | 公开仓安装后默认提供看板；私有仓由超管在仓库列表开启看板后公开 |

另外，你需要在 GitHub 上有该仓库的管理权限，并且是控制台的超管（或找超管帮你点）。

## 1. 把仓库加入管理面

### 1.1 安装 GitHub App

打开安装页，选择你的账号或组织，勾选这个仓库：

```
https://github.com/apps/agent-ci-infra-bot/installations/new
```

> 这一步只能你本人做：GitHub 要求仓库所有者确认授权，别人代替不了。

装好后 GitHub 会跳回控制台。

### 1.2 同步到管理面

控制台仓库列表右上角点 **同步安装列表**（或让超管点）。

新仓库会以 `未启动` 出现，右侧有 `已移出安装` 之类的 badge 说明当前安装状态。

### 1.3 启动项目

在该行点 **启动**：

- 选择模型（决定后续检视/开发用哪个模型）；
- 决定是否打开 **开发** 开关（关掉的话 bot 只会检视，不会改代码）；
- 确认后这一行变成 `工作中`，`已启用`。

启动之后 bot 才会收这个仓库的 Issue / PR 事件。

## 2. 一键接入（自动化部分）

仓库列表中直接用 **看板** 开关控制单仓看板与公共 Dashboard 汇总，无需执行接入流程，也无需启动检视或开发项目：

- 公开仓默认开启，私有仓默认关闭。
- 开启私有仓后，其看板数据无需登录即可访问，请确认允许公开。
- 关闭后立即停止对外展示，包括已经生成的快照；设置在刷新、同步安装和重启后保留。
- 以前已明确启用的私有仓会保留开启状态。已保存的开或关在仓库可见性变化后也保持不变；未保存选择的仓库按新可见性使用默认值。

**接入门禁** 是一段和 agent 的对话，不改变看板开关：

1. **先看五层介绍**：点「接入门禁」后，对话框先说明 build、pr-ready、pr-merge、daily、release 各在什么时候运行。此时不会读写仓库，也不会创建分支或 PR。
2. **开始适配**：控制面用只读安装令牌查看默认分支：语言、根目录的构建和依赖文件（`package.json`、`pyproject.toml`、`Makefile`、`go.mod`、`Cargo.toml` 等）、已有 workflow 及其命令、是否已有 `ci.yml` 或 `ci-gates.json`、有没有未合入的门禁 PR，以及默认分支是否启用 merge queue（先看规则集，再看分支保护；判断不了就在对话里问你）。
3. **和 agent 定方案**：项目已启动并选了模型时，agent 用项目默认模型和同一套仓库只读工具提出工具链、安装命令和各 lane 的命令，并注明来源；不确定的命令留空并在对话里问你。你可以回复它，也可以直接修改右侧方案。仓库还没启动或没有可用模型时，右侧是只按仓库中确定的命令整理的初步方案，由你补充后确认。确认之前，控制面不写仓库、不推分支，也不运行仓库里的脚本。
4. **确认后开 PR**：点「确认并创建门禁 PR」后，控制面按你确认的那一版方案生成文件并开 PR。

门禁 PR 的内容：

- 门禁 workflow：默认是 `.github/workflows/ci.yml`。仓库已有 `ci.yml` 时不会覆盖，门禁 job 放在 `.github/workflows/ci-gates.yml`，PR 正文说明怎样并进 `ci.yml`。触发事件、权限和 job 结构由控制面决定；pull_request 上报告 PR head 提交，不是 GitHub 的合并提交。
- `.github/ci-gates.json`：各 lane 的命令。空 lane 运行时报告 `not_applicable`，只说明还没有配置检查，不表示检查通过。
- `scripts/gate/gate.mjs`：从 `agent-CI-Infra/CI-workflow` 复制；仓库已有时沿用。
- `.github/workflows/release.yml`：版本标签（如 `v1.2.3`、`v1.2.3-beta.1`）触发 release lane；仓库已有时不覆盖。框架不含 PyPI、npm 或镜像发布步骤。

**merge queue**：默认分支启用了 merge queue 时，这次只提交进入队列之前的门禁，也就是 pull_request 上的 build 和 pr-ready；不包含 `merge_group`，也不包含 push 到默认分支后才运行的门禁，pr-merge 留空。daily 和 release 有命令时照常保留。没有 merge queue 的仓库保留 CI-workflow 的完整事件（pull_request、merge_group、push 到默认分支、有命令时的定时任务）。如果之后要把 `gate` 设为合并队列的必需检查，需要先给门禁 workflow 加上 `merge_group`，否则队列会一直等这项检查。

默认分支上已有 `.github/ci-gates.json` 的仓库视为已接入，对话直接说明这一点，不再开覆盖它的 PR；需要调整时直接改这个文件。

使用时，先合并并配置门禁 PR，再到项目页「发版本」检查版本和目标提交。相对上一枚可达的合法版本标签没有新提交时，页面说明跳过，不能确认；没有上一枚标签则按首次发布处理。填写的版本必须按 SemVer 高于上一枚可达版本标签，否则页面给出可填写的更高版本，不能确认。有新提交时，人确认后创建标签，仓库 Release Actions 成功后生成草稿，再由人点击「正式发布」。定时发版本和自动计算版本号不在当前框架范围内。

公开页面与原看板使用同一套字段、统计方法和版式，由 webhook 端口 8791 托管，无需控制台登录。管理端口 8792 的控制台看板保持原样，不提供 `/dashboard/` 和 `/boards/`。

### 2.1 私有仓库的看板开关

私有仓默认不出现在公共页面。超管在仓库列表开启「看板」后，bot 在本地保存公开授权，并使用源仓只读安装令牌采集，后续由已验证 webhook 更新。不需要外部 dashboard 仓、登记 PR 或 `PRIVATE_SOURCE_TOKEN`。关闭开关会立即隐藏该仓的单仓页面和 Dashboard 数据；未开启的路径返回 404。

首次采集尚未完成时，页面或数据接口会提示等待；后台失败时保留上一次有效快照并退避重试。请先在安装向导验证 webhook 公网地址，接入结果才会生成这个入口上的稳定链接。

## 3. 需要你亲手确认的事项

自动化到"PR 开出来"为止，门禁检查内容和开发授权仍留给人把关：

1. **确认方案并合并门禁 PR**：在接入对话里确认各 lane 的命令，PR 上的 Actions 跑过后再合入；是否在 Release workflow 里发布包或镜像由本仓库开发者决定；空命令 lane 只表示还没有配置；
2. **确认私有仓快照是否可以公开**：需要公开时，由超管在仓库列表开启看板；公开仓不需要这一步；
3. **给需要开发的 Issue 加 `bot-develop` 标签**：bot 只处理带这个标签的 Issue，这是"允许 bot 改代码"的唯一开关。

## 4. 接入之后会发生什么

```
你 push / 开 PR
  └─ CI 跑门禁（CI-workflow 的 workflow）
       └─ 上传 ci-gates-reports
            └─ 已验证 webhook → bot 后台采集 → 本地快照
                 └─ <webhook 公网地址>/boards/<owner>/<repo>/
```

- **检视**：你开 PR 后 bot 会自动检视并评论；也可以在 Issue/PR 里 @ 它再检视一次；
- **开发**：给 Issue 加 `bot-develop` 后，bot 会开分支改代码并回 PR；
- **看板**：已验证 webhook 触发后台采集，单仓快照和 Dashboard 汇总一起更新，不再部署 Pages。

## 5. 常见问题

**列表里"门禁未知 / 看板未知"？**
检查器会实时读你的仓库确认。出现未知通常是 App 没装到该仓库、或安装权限还没被批准。装/批之后点一次同步即可。

**"单仓看板"报缺少权限？**
看板采集仅使用源仓只读权限：Contents、Issues、Pull requests、Actions、Metadata。安装需要允许读取对应数据；不需要 Pages、Administration 或 Workflows 写权限。

**私有仓库能接吗？**
能。安装 App 不代表同意公开私有仓；超管在仓库列表开启看板后，快照才会公开，由 webhook 更新。无需配置额外 secret。

**想撤销某个项目的接入？**
控制台项目行的 **删除** 只清理本系统记录（仓库、策略、运行记录），**不会**卸载 App，也不会删除 GitHub 上的仓库。GitHub 侧请自行处理。

**接入失败了怎么排查？**
接入对话会写明原因和错误码（如 `app_permissions_missing`、`template_app_not_installed`、`repository_empty`），对着提示处理后再次确认即可，会复用同一个分支；确认前可以展开「预览将提交的文件」查看完整内容。看板的问题（如 `public_address_not_verified`、`collection_failed`）显示在仓库列表的看板开关旁。
