# 接入指南：把一个代码仓交给 launchpad

这份文档面向**使用 bot 的仓库维护者**：从"我有一个代码仓"到"bot 在这个仓库开始工作"。主线是两步：在 GitHub 上安装 App，然后在控制台的**管理助手**里让助手只读分析仓库、回答几个关键问题、确认后启动并完成配置。后面还有看板、CI 怎么改，以及需要你亲手做的几步。

---

## 访问入口

| 入口 | 地址 | 用途 |
| --- | --- | --- |
| **管理面（控制台）** | https://agent-ci-infra-bot-admin.llmbots.co/ | 接入仓库、管理项目、用户与仓库授权 |
| **公共 Dashboard** | <公网入口地址>/dashboard/ | 看所有已登记仓库的 PR、Issue、贡献者和版本等社区指标 |
| **单仓看板** | `<公网入口地址>/boards/<owner>/<repo>/` | 单个仓库的 Issue、PR、CI 运行历史、定时运行结果的趋势图和发版，`<owner>/<repo>` 用小写；任何仓库开启后就有内容，不需要按约定配置 CI |
| **GitHub App 安装页** | https://github.com/apps/agent-ci-infra-bot/installations/select_target | 把 bot 安装到你的账号/组织 |

### 管理面怎么登录

1. 打开 https://agent-ci-infra-bot-admin.llmbots.co/ ；
2. 如果出现 Cloudflare Access 的验证页，先填**你的邮箱**，收邮件验证码完成验证（这一步是网关鉴权，不是 bot 账号）；
3. 进入控制台登录页后，用管理员分配的**用户名 + 密码**登录；
4. 首次部署时首页会显示「创建第一名管理员」，由部署者初始化，之后这里只提供登录。

登录后，系统超级管理员从顶部「全局设置」进入部署用的「系统初始化」（`#/settings/onboarding`），在第三步配置 GitHub 账号登录（它配置的是整个部署，和下面第 2 节在管理助手里接入单个仓库不是一回事）。系统初始化仅系统超级管理员可用；普通使用者通常是**项目管理员**，只看到自己有权管理的仓库，超级管理员能看到全部。

GitHub 登录使用独立 OAuth App：在 OAuth Apps 中登记 Bot 入口和登录 Callback URL，复制这个 OAuth App 的 Client ID 和 Client secret，再回本页保存启用。仓库连接使用另一份 GitHub App，默认仅申请仓库级权限，无需配置组织级权限。更换仓库 App 不会切换登录配置；已有登录 Secret 留空保留。升级前复用仓库 App 登录的配置会显示迁移说明。详细配置见[GitHub 用户登录](onboarding.md#github-用户登录)。

> 忘记密码或需要账号，找超级管理员在「用户管理」里重置或新建；控制台的写操作需要登录会话，长时间无操作后会要求重新登录。

## 0. 开始之前

| 你的仓库需要 | 说明 |
| --- | --- |
| 你是仓库的管理员 | GitHub 上的仓库 Admin 或组织 owner 才能在管理助手里接入并启动（或申请启动）仓库；超级管理员也可以 |
| 已安装 GitHub App | 管理助手读仓库、建标签用 App 的安装令牌；改 CI 的 bot PR 要用 App 的 Workflows 权限 |
| 至少有一个提交 | 空仓库没有可读的事实，先推送代码 |
| 不限语言 | Node、Python、Go、Rust、Java 等都可以；不要求 `package.json` 或 npm 锁文件 |
| 是公开或私有仓库 | 公开仓安装后默认提供看板；私有仓由超管在仓库列表开启看板后公开 |

项目不需要事先启动：即使你名下还没有任何已启动的项目，只要有已安装待接入的仓库，就能打开管理助手先做只读分析，确认后再启动（见 2.4）。

## 1. 安装 GitHub App

### 1.1 安装

打开安装页，选择你的账号或组织，勾选这个仓库：

控制台仓库列表右上角点 **同步安装列表**（或让超管点）。新仓库出现在项目列表的「待接入的仓库」里，身份页也会列出它。

## 2. 在管理助手中接入仓库

仓库接入直接由**管理助手**（`#/management` 与 `#/projects/<id>/management`）在常规会话里完成，没有单独的受限向导页：助手先只读分析仓库，讲清楚各能力上限下 bot 会做什么，提出最多 5 个关键选项，等你确认后再启动仓库并按确认项完成配置。你不需要事先知道各项设置分散在哪一页。

### 2.1 打开管理助手

- 新仓库：在项目列表「待接入的仓库」、身份页或超级管理员仓库列表里，点仓库旁的 **开始接入**，会自动进入管理助手（`#/management`）并在输入框预填针对该仓的接入提示词；
- 已经启动的项目：进入该项目的管理助手（`#/projects/<id>/management`），在「推荐列表」点 **运行仓库接入助手**，输入框会预填配置核对提示词，助手对照当前已生效设置只提出建议调整的项，不确认就不改；
- 你也可以直接在管理助手（或已绑定的飞书个人私聊）里对助手说「帮我接入 `<owner>/<repo>`」；旧的 `#/onboarding/<仓库 id>` 书签会自动跳转到管理助手并预填提示词。

### 2.2 只读分析与个人电脑

检查或补充输入框里的提示词后点击 **发送**。在未确认前，助手只读仓库（`github_read`、`github_search`、`read_job_log` 均支持你管理的未启动已安装仓库，未启动前严格拒绝 `github_write`）：读取 README、根目录 `AGENTS.md`／`CONTRIBUTING.md`、`.github/ISSUE_TEMPLATE/`、`.github/CODEOWNERS`、目录结构、语言与构建测试文件、`.github/workflows/`、`.agents/skills/`（仅 `.agents/skills/` 视为本仓库给协作 Agent 准备的 skill，其他业务目录里的 `SKILL.md` 视为项目自身资产）、默认分支保护情况、现有标签与用法、近期 Issue／PR 与 Actions 运行记录。

因为接入运行在标准管理助手会话中，部署启用了助手电脑时，你在 0 个已启动项目阶段即可挂载并使用自己的个人虚拟电脑（`run_command`、`read_file`、`write_file`）配合分析，也可以使用管理助手的独立子任务（`start_own_task`）和配置的任意后端（Native / Pi / Codex / Claude Code）。回复流式显示，随时可以点 **停止**。

### 2.3 画像与关键选择

助手在对话中给出简洁的**仓库画像**（用途、技术栈、协作与检视习惯、现有协作文件与 `.agents/skills/`、CI 工作流与默认分支保护情况、现有标签、读过的来源），说明三种能力上限（`read` 只读问答、`comment` 检视与打标签及失败运行分析、`develop` 进一步开发 Issue 并开 PR），并针对仓库本身尚未定下的地方提出最多 5 个问题（每题附选项、推荐项与理由）。仓库已有的约定和配置直接沿用；缺少 `AGENTS.md`、Issue 模板、分支保护等协作项时，仅在与你期望的用途直接相关时顺带给出一两句轻量的可选建议，绝不作为接入前提或打分清单。你直接在对话里用自然语言确认或调整选择即可。

### 2.4 启动（或申请启动）与应用配置

你在对话中明确确认后，助手按顺序通过标准工具完成启动与配置，每一步都会在对话的「执行进展」中留下真实回执：

| 配置项 | 生效方式与位置 |
| --- | --- |
| 启动或申请启动 | 未启动仓库调用 `start_repository`：超级管理员或受信任组织（#848）的仓库管理员直接启动；未受信任组织提交启动申请（见下） |
| 能力上限、测试命令、检视语言 | `management_command` `project.update`（测试命令保存时不直接执行，由首个任务或 CI 任务验证） |
| 监听与触发 | `management_command` `manager.update` 配置 Manager 接收的 Issue、PR 和 Actions 事件开关 |
| 本仓库约定 | 作为独立的 `## 本仓库约定` 段落追加到 Manager 提示词（`manager.update`）和各启用工作角色提示词（`roles.update`），不覆盖原有内容 |
| GitHub 标签 | 先核对现有标签，仅对缺失标签调用 `github_write POST /labels` 新建（能力上限需至少 `comment`；`develop` 档默认确保开发进度标签存在），已有同名标签保持不变 |
| 定时检查与准点触发 workflow | `management_command` `schedule.register`（`workflow: "manager.check"`），项目尚无服务身份时按当前管理员委托自动创建，见[定时任务](schedules.md#定时触发-workflow) |
| 协作说明文件或仓库 skill（可选） | 仅当你明确希望由 bot 代提 PR 新增或修改（如根目录 `AGENTS.md`、`CONTRIBUTING.md`、`.github/ISSUE_TEMPLATE/**`、`.github/CODEOWNERS` 或 `.agents/skills/<名称>/**`）时，统一走正常的 PR 开发流程：将项目能力上限开启为 `develop` 后，通过 `management_command` `task.create` 创建标准开发任务（bot 跑验证并开可检视 PR，人工检视合并后生效，不设特殊快捷通道） |
| CI 建议（修改 `.github/workflows/`） | 助手调用带 `workflow_changes: true` 的 `task.create` 时**不会直接建单**，而是在控制台对话里生成一张「执行前确认」卡片；由项目管理员在控制台点击 **确认执行** 后才正式创建开发任务（bot 开 PR，人工检视合并，见 3.2） |

**未受信任组织的启动申请（#933）**：当仓库所属组织尚未被超级管理员设为受信任组织时，仓库管理员确认启动会生成一条待处理的启动申请。超级管理员在控制台「待处理」页顶部看到申请卡片（绑定了飞书私聊的还会收到通知，可直接回复「同意」或「拒绝 + 原因」处理），同意时可选择模型、能力上限并可顺带信任该组织；拒绝须写明原因。申请人在等待期间可在管理助手里随时让助手查询申请状态或撤回申请；同意启动后即可继续在管理助手里让助手应用其余配置。

### 2.5 超级管理员直接启动

超级管理员也可以不经管理助手分析，直接在自己的仓库列表里点未启动仓库的 **启动**：选模型、能力上限，组织还没受信任时可以勾选「信任 …」。超级管理员在「全局设置 → 项目管理 → 受信任的组织」信任一个组织后，该组织仓库的管理员在管理助手确认启动（或调用激活接口）时直接启动，默认使用组织的模型和能力上限，资源用全局默认值，机器配置仍只由超级管理员修改。撤销信任只影响以后的启动，已启动的项目照常运行。信任、撤销和每次启动都写入审计。

启动之后 bot 才会收这个仓库的 Issue / PR 事件。

## 3. 看板与发版本

仓库列表中直接用 **看板** 开关控制单仓看板与公共 Dashboard 汇总，无需在管理助手里接入仓库，也无需启动检视或开发项目：

- 公开仓默认开启，私有仓默认关闭。
- 开启私有仓后，其看板数据无需登录即可访问，请确认允许公开。
- 关闭后立即停止对外展示，包括已经生成的快照；设置在刷新、同步安装和重启后保留。
- 以前已明确启用的私有仓会保留开启状态。已保存的开或关在仓库可见性变化后也保持不变；未保存选择的仓库按新可见性使用默认值。

**发版本**：在项目页「发版本」确认版本后，bot 打版本标签，标签触发仓库的 `release.yml`；运行成功后，bot 按已核实的提交和 PR 写发行说明，创建 Release 草稿，由人点击「正式发布」。

使用时，仓库需要有发布用的 CI（`.github/ci-gates.json` 和运行它的 `ci.yml`）和版本标签触发的 `.github/workflows/release.yml`，再到项目页「发版本」检查版本和目标提交。相对上一枚可达的合法版本标签没有新提交时，页面说明跳过，不能确认；没有上一枚标签则按首次发布处理。填写的版本必须按 SemVer 高于上一枚可达版本标签，否则页面给出可填写的更高版本，不能确认。有新提交时，人确认后创建标签，仓库 Release Actions 成功后生成草稿，再由人点击「正式发布」。定时发版本和自动计算版本号不在当前框架范围内。

公开页面与原看板使用同一套字段、统计方法和版式，和控制台一起由业务端口 8791 托管，但无需控制台登录。控制台里的「任务看板」页是另一页面，仍需登录。

### 3.1 私有仓库的看板开关

私有仓默认不出现在公共页面。超管在仓库列表开启「看板」后，bot 在本地保存公开授权，并使用源仓只读安装令牌采集，后续由已验证 webhook 更新。不需要外部 dashboard 仓、登记 PR 或 `PRIVATE_SOURCE_TOKEN`。关闭开关会立即隐藏该仓的单仓页面和 Dashboard 数据；未开启的路径返回 404。

首次采集尚未完成时，页面或数据接口会提示等待；后台失败时保留上一次有效快照并退避重试。请先在系统初始化验证公网入口地址，接入结果才会生成这个入口上的稳定链接。

### 3.2 CI 改动走 bot PR

bot 不按固定模板给仓库配 CI。CI 改动和其他代码改动一样，以 bot PR 交付，由人检视、合并：

1. **提出并确认改动**：在管理助手对话里讨论好 CI 方案后，助手会生成一张带 `workflow_changes: true` 的「执行前确认」卡片，由项目管理员在控制台点 **确认执行** 创建开发任务；也可以由项目管理员在控制台「新建任务」里写明想要的 CI（例如 PR 上跑哪些检查、哪些放进定时运行），交付类型选「可检视的代码 PR」，勾选「允许修改 .github/workflows/（CI 改动）」。只有项目管理员能确认这一项。
2. **bot 按仓库实际情况改**：任务和其他开发任务一样在项目电脑里工作。agent 读仓库已有的脚本、Makefile、构建文件和 workflow，改 workflow，跑项目的测试命令和独立 QA，再推送自己的 bot 分支、开 PR。推送时才向 GitHub App 申请 Workflows 写权限，前提是安装已授予。
3. **人合并后才生效**：默认分支上的 workflow 只在人合并这个 PR 后才变化，必需检查照常运行。

没有这样确认过的任务不能改 `.github/workflows/`：Issue 开发和普通开发任务推送改到 workflow 的分支时，GitHub 拒绝发布；Manager 和其他角色的 `github_write` 也拒绝写这个目录。agent 会在任务里说明需要一个确认过的 CI 任务。

App 的 Workflows 权限仍然申请，只用于上面这类确认过的 CI 任务。安装没有授予时，确认过的 CI 任务也推不了改到 workflow 的分支，仓库列表的权限提示会写明「经确认的 CI 改动」受影响。

已经用 `.github/ci-gates.json` 和 `scripts/gate/gate.mjs` 配过门禁的仓库，这些文件归仓库自己维护，照常运行；已经开出的门禁 PR 也照常可以合并。「发版本」的预检仍读取它们。

## 4. 需要你亲手确认的事项

自动化到"PR 开出来"为止，CI 内容和开发授权仍留给人把关：

1. **检视并合并改 CI 的 PR**：PR 上的 Actions 跑过后再合入；是否在 Release workflow 里发布包或镜像由本仓库开发者决定；
2. **确认私有仓快照是否可以公开**：需要公开时，由超管在仓库列表开启看板；公开仓不需要这一步；
3. **决定哪些 Issue 交给 bot 开发**：能力上限含开发时，Manager 只在有依据时开发一个 Issue：有人加了开发标签（标签名在「基本设置 · 标签」查看和修改）、triage 以上权限的维护者在评论里提出，或者 Manager 提示词里的规则允许（在管理助手接入时确认并写入 Manager 提示词的「简单问题」约定就是这样的规则）；外人的评论不算；
4. **打开分支保护和必需检查**：bot 的 Manager 默认有 Contents 写权限，可以经 `github_write` 写分支（包括默认分支），并按项目的[自动合并策略](workflows.md#项目自动合并策略)合并 PR（默认只在维护者明确要求时合并）；在默认分支上直接写入也按这个策略（默认要维护者请求）。控制面不替它跑合并前的校验，见[角色池](role-pool.md#authorized-merge)。所以请给默认分支打开分支保护（或规则集），把仓库的 CI 检查设为必需检查，启用 merge queue 时要求经队列合入；这样 bot 和人的合并都要先过这些检查。不希望 Manager 合并时，在「角色 → Manager」把 Contents 改成只读。

## 5. 接入之后会发生什么

```
你 push / 开 PR
  └─ 仓库自己的 CI 运行
       └─ 已验证 webhook → bot 后台采集 → 本地快照
            └─ <公网入口地址>/boards/<owner>/<repo>/
```

- **检视**：你开 PR 后 bot 会自动检视并评论；也可以在 Issue/PR 里 @ 它再检视一次；
- **开发**：能力上限含开发时，Issue 有了开发依据（开发标签、维护者的评论或提示词里的规则），bot 会开分支改代码并回 PR；
- **看板**：已验证 webhook 触发后台采集，单仓快照和 Dashboard 汇总一起更新，不再部署 Pages。

## 6. 常见问题

**列表里"门禁未知"？**
检查器会实时读你的仓库确认。出现未知通常是 App 没装到该仓库、或安装权限还没被批准。装/批之后点一次同步即可。

**"单仓看板"报缺少权限？**
看板采集仅使用源仓只读权限：Contents、Issues、Pull requests、Actions、Checks、Metadata。安装需要允许读取对应数据（没有 Checks 时定时运行的结果只从产物读取）；不需要 Pages、Administration 或 Workflows 写权限。

**单仓看板 CI 页的「定时运行」图怎样才有数据？**
有定时触发（`schedule`）的 workflow 在默认分支上的运行（定时和手动触发都算）会被逐次读取，看板依次找：该运行检查套件里检查运行输出中的 Markdown 表格（例如测试报告类 action 写的检查结果），运行产物里的 JUnit XML 或简单 JSON（`{"metrics": [{"name": "tests", "value": 120, "unit": "count"}]}`），都没有时只画运行和各 job 的耗时。表格的列、JUnit 的总数和 JSON 的名称都成为可选指标；每次运行最多读 3 个不超过 10 MiB 的产物。Actions 的 step summary（`$GITHUB_STEP_SUMMARY`）GitHub 不经 API 提供，看板读不到。

**私有仓库能接吗？**
能。安装 App 不代表同意公开私有仓；超管在仓库列表开启看板后，快照才会公开，由 webhook 更新。无需配置额外 secret。

**想撤销某个项目的接入？**
控制台项目行的 **删除** 只清理本系统记录（仓库、策略、运行记录），**不会**卸载 App，也不会删除 GitHub 上的仓库。GitHub 侧请自行处理。

**改 CI 的任务发布失败了怎么排查？**
任务页写明原因和错误码。GitHub 拒绝推送改到 `.github/workflows/` 的分支，通常是任务没有确认为 CI 改动，或 App 安装没有授予 Workflows 写权限。看板的问题（如 `public_address_not_verified`、`collection_failed`）显示在仓库列表的看板开关旁。
