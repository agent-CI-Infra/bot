# 管理 API

管理页面的操作都经由下列接口。它们和管理页面、OAuth 与 App 回调、Webhook 在同一个业务端口（容器 `8791`，宿主默认 `127.0.0.1:8791`），对外经同一个 HTTPS 入口访问；Webhook 和外部执行端路径按自己的签名或令牌认证，不需要浏览器会话。部署见[部署细节](deployment.md)。

除初始化状态、初始化、登录和健康检查外，管理 API 都需要登录会话。登录／初始化响应设置 `HttpOnly; SameSite=Strict` Cookie，并返回 `csrf_token`；之后的写请求必须提供同值 `X-CSRF-Token` 和 `Content-Type: application/json`。登录后 `GET /api/auth/me` 可读取当前会话的 CSRF 值。接口不接受额外字段，不支持传入 `role` 将自己升级。HTTP 失败只返回稳定错误码，不回显输入或内部异常。经 Cloudflare 等入口访问时，502、504 响应的正文会被入口换成它自己的错误页，错误码随之丢失；控制台此时提示“入口网关返回了错误页面”，不显示 JSON 解析错误。需要用户据此处理的错误不用这两个状态码。

项目列表 `GET /api/repositories`、`GET /api/installations` 和 `GET /api/installations/hidden` 支持 `repository_id,account_id,owner_id` 筛选；先应用权限和筛选，再按原顺序分页。传入 `limit` 或 `offset` 时每页默认 50 条、上限 100 条，`offset` 默认 0；不传分页参数时保留完整列表响应，供其他页面使用。项目页和任务数刷新固定请求当前页的 50 条，再按 `owner_id` 分组展示；分组不改变权限或筛选。

管理查询 `get_effective_config` 的 `task_creation:{allowed,reason}` 是当前身份、项目、安装、预算与凭据条件的只读预检。`allowed:true` 不授予代码或 PR 写入；提交 `task.create` 时仍执行原有版本、授权与软件交付检查。

`GET /api/tasks/:id/logs` 默认按时间顺序返回最近 100 条日志。`limit` 为 1–100，`before` 向前读取更早页，`after` 向后读取新增页，两种游标不能同时提供。游标取响应 `log_page.first_sequence` 或 `last_sequence`，以日志追加序号为准，不依赖可能相同的时间戳；`has_older` 和 `has_newer` 表示当前读取方向是否还有下一页。客户端加载历史页后保留最早游标，轮询新增页时继续使用已读取的最大序号。每个请求都重新核对任务所属项目的权限，历史模型日志的私有字段在读取投影中过滤，新的 Pi 日志在保存前统一移除私有字段。


Webhook 对原始字节计算 HMAC-SHA256 并以恒定时间比较，验签后才解析和关联仓库。签名错误返回 401，未知入口返回 404，非法 JSON 返回 400，超过 2 MiB 返回 413。被拒投递（未知入口、验签失败、正文超限、非法 JSON、缺事件或投递号）只归档摘要 `{rejected,bytes,truncated,sha256}`（最多 256 字节）和四个识别用请求头 `x-github-event,x-github-delivery,content-type,user-agent`（合计最多 1 KiB），不保存正文；拒绝行最多 500 条、只保留 7 天，超额或超龄的行在每次拒绝时裁剪，`pruned_total` 记录累计裁剪数。被拒投递不写入正文，未认证请求的存储不会随请求体大小增长；合法投递的正文、响应记录与去重语义不变。请求头中的认证、签名和 Cookie 等内容脱敏。请求正文、响应记录和 `(account_id,endpoint_id,delivery_id)` 去重键在同一个 SQLite `BEGIN IMMEDIATE` 事务提交后才返回成功；写库失败返回 503 且回滚去重。重复投递保存独立档案，响应标记 `duplicate:true`。失败投递不消费去重键，重试可成功。空仓库配置、未启动或已禁用的仓库只归档，不生成任务。

项目列表接口 `GET /api/repositories` 与超级管理员的 `GET /api/installations` 在每个仓库上返回 `running_tasks` 和 `queued_tasks`。`GET /api/installations` 另返回 `permission_missing`：仍在安装列表中的仓库所缺权限（`permission,required,current`；机器人账号为 `repository_role`），未读到授予权限或不在安装列表时为 null；`events_missing` 是安装未订阅的必选事件名，未知或已移出安装时为 null，机器人账号为 `[]`；`access_gaps` 对照全部功能（不论是否开启）列出缺口，每项为 `kind,name,required,current,features`：`kind` 是 `permission`、`event`、`role`（机器人账号的仓库角色）或 `account`（机器人账号不能用只走 GitHub App 的发版本、接入门禁和 Actions 失败分析）；`features` 是因此不能用的功能，空数组表示只低于接入基线；授予权限或 App 安装事件尚未读取、或不在安装列表时为 null。基线之外，接入门禁还需要 `workflows: write`，Actions 失败分析还需要 `workflow_run` 事件；`review_threads`（再次检视时关闭作者已修复的行内意见）需要 `contents: write`，缺少时检视照常发布，只是不关闭讨论串。`actions_failures_enabled` 是该仓库的 Actions 失败分析开关。`POST /api/installations/permissions/check` 返回重新读取后的完整仓库行。`GET /api/accounts/{id}/permissions` 的 `app.feature_gaps` 列出 App 定义在基线之外还缺、只有部分功能需要的项，不影响 `ok`。`permissions_stale` 表示权限／事件尚未完整读取，或已超过 10 分钟未重读。前者仅统计实际执行阶段，后者统计 queued；配置等待、环境等待与已结束任务不计入执行中。返回范围沿用项目管理员的仓库权限。列表开关调用 `PATCH /api/repositories/{id}/policy`，仅提交本次切换的 `review_enabled` 或 `development_enabled`，不更改项目总启用状态。

看板筛选格式为 `[{"field":"object_type","value":"pr"},{"field":"text","value":"research"}]`，最多 20 条，条件之间为“且”。支持 `repository_id`（仓库 ID）、`object_type`（`all`／`issue`／`pr`，默认全部；Issue／PR 限制结果为该对象类型，单独筛发版本时保留但忽略对象类型条件）、`category`（`review`／`development`／`release`）、`execution_status`（`running,queued,failed,completed,waiting,other`）、`bot_stage`（`unreviewed,reviewing,reviewed,developing,developed,attention`）、`text`（对象编号可带 `#`，否则按标题或发版本号匹配）、`include_closed`（布尔，默认 false，只影响对象卡片）。`group_by` 为 `bot_stage,repository,execution_status,category` 或当前用户的单选字段 ID；自定义字段空值列 ID 为 `unassigned`。筛选、标准维度和折叠列可在浏览器先预览，点击“保存视图”后持久保存。每页最多 100 张工作卡片；`work_count`、`column_counts` 为筛选范围内全量计数，`counts` 为去重对象数，`release_count` 为筛选后的发版记录数。

任务列表、任务详情、项目最近任务和看板关联任务现在带 `metrics`：`runtime_ms`（累计已观测执行时长，不含排队／等待）、`running`、`complete`（历史或进程中断时可能不完整）、`input_tokens,output_tokens,cached_input_tokens,cache_hit_rate`、`requests,usage_missing_requests,cache_missing_requests,unpriced_requests` 和按币种分开的 `costs`。缓存是输入的子集，命中率用累计缓存 token 除以累计输入 token；缺少必要统计时返回 null，不用 0 冒充。`complete:false` 时显示的是已经观测到的部分。

`GET /api/costs` 的 `tasks.days` 为按任务 `created_at` 的本地日、仓库与工作类型聚合的行，`tasks.summary` 为日期范围内按工作类型的汇总（按工作类型目录顺序），`tasks.undated` 单独列出授权仓库内无可靠创建日期的历史任务，不进入日期范围内总数或每日分桶。所有任务都统计：`workflow`（沿用旧字段名）是工作类型 id，通用回复任务（包括原自定义工作流的任务）为 `reply`，其他是任务种类（如 `review.issue`、`actions.failures`、`release.observe`）；`name` 是工作类型名称。每行还含 `kind,count,runtime_ms,incomplete_tasks,running_tasks`；整段累计执行耗时计入创建日，不跨日拆分，运行中含当前已观测执行区间，不含排队与等待。缺失计时或未观测到时长的不完整历史计时返回 null，已有部分则仅累计已观测值并标记不完整。仅覆盖控制面账本与任务，不采集外部执行端自行调用或项目内其他服务。

模型创建和带 `version` 的 PATCH 还可提交 `pricing:{currency,input_per_million,output_per_million,cache_per_million}`，单价为每百万 token 的非负数（最多 1000000）。`pricing:null` 清除单价；读模型时返回当前单价，原有模型凭据及共享模型编辑权限不变。每次模型请求保存价格快照，费用为 `((输入-缓存)×输入单价 + 缓存×缓存单价 + 输出×输出单价) / 1000000`。缺少用量或单价时费用为 null；未返回缓存数据且缓存价不同于普通输入价时，也不能完整计价。统计页的费用和 token 只汇总所选币种及尚未定价的请求，币种之间不作换算；另一币种的请求数在 `other_currencies` 里单独列出，所以切换币种不会让请求看起来凭空消失；币种不影响任务统计。

获取模型列表和测试模型的上游结果都在成功响应里返回：`ok` 表示上游是否成功，`status` 是上游的 HTTP 状态码（没有收到响应时为 null）。列表成功时返回 `models_url,total,truncated,models`，按名称排序，最多 200 个 id；测试成功时返回 `chat_url`、`model`（上游答复中的模型名）、`reply`（回复摘录，最多 200 个字符）、`finish_reason` 和 `elapsed_ms`。失败时返回 `error`（`upstream_http_error`、`upstream_timeout`、`upstream_unreachable`、`upstream_redirect`、`upstream_response_invalid`、`upstream_response_too_large`）和简短的 `message`：它只取自上游 JSON 的错误字段（`error.message`，或字符串形式的 `error`、`message`、`detail`、`msg`），重定向时是 `Location`，连接失败时是错误码；其他响应正文一律不回显。两类请求都在 15 秒后超时、不跟随重定向，结果中出现的 Key 先整体替换为 `[REDACTED]`，再截断。模型 URL 只接受 http(s)，不能带用户名、密码、查询串（`?`）或片段（`#`），否则保存、解析、获取列表和测试都返回 400 `invalid_api_url`；这条规则之前保存的这类 URL 也不能获取列表或测试。测试请求的内容是一句不含项目数据的探测，只带 `max_completion_tokens: 32`，不带 `max_tokens`；任务中的模型请求不受影响，仍只带一个输出上限字段，数值 8192。


供应商连接的批量管理沿用模型范围和规范化请求地址，不引入跨项目凭据共享：

- `POST /api/models/provider`：`{repository_id?, api_url, api_key, model_names:[...]}`，一次创建供应商下的多个模型，至少一个、最多 200 个。相同范围已有该请求地址返回 `409 provider_already_exists`。
- `PATCH /api/models/:id/provider`：以模型 ID 定位所在供应商；必须提供组内全部模型的 `versions:[{id,version}]`，可提交 `api_url`、非空 `api_key` 和待添加的 `model_names`。Key 空白保持原值。组成员、版本发生变化返回 `409 version_conflict`；事务内更新全部连接并添加新模型，返回不含 Key 的 `models`。
- 同一路径提交 `{versions, revoke_key:true}` 统一撤销组内 Key；不能同时提交 URL、新 Key 或新增模型。项目选择和已有计费单价不变。
- `POST /api/models/:id/upstream` 可带 `version`、草稿 `api_url`／`api_key`，在编辑权限下使用草稿或已保存 Key 获取列表，不保存这些值；空 Key 使用该模型已保存的 Key。旧的单模型 API 保持兼容。

任务运行、来源保留上限及详情投影的完整说明见 [Task trace](task-trace.md)。文本交付按原始 UTF-8 正文 2 MiB 限制，JSON 转义后的包裹体另有 16 MiB 上限；超限保留路径、版本、读取/脱敏状态及哈希，仅省略正文。

项目记忆（沿用项目权限）：`GET/POST /api/repositories/:repo/memories` 查询/建立条目，GET 支持 query、module、source、kind、status、baseline、after、limit（1–50）、include_superseded=1；`GET/PATCH .../memories/:id` 读取指定 revision 或按 expected_revision 更新，支持 supersedes 同项目 ID 数组；`GET .../:id/versions` 查询修订与来源关系；`POST .../:id/document` 从真实 GitHub PR 和文件验证仓库文档关联。具体契约见 [Project memory](project-memory.md)。

角色协调：`GET/PUT /api/repositories/:repo/roles` 查询/配置 RoleDefinitionV2（PUT 必须带 `expected_revision`，冲突返回 409；校验错误的响应带 `field`，指出出错的配置字段），GET 还返回 Harness 能力矩阵、逐项权限定义 `permission_items`、共用系统提示词 `system_prompt`、可编辑角色模板 `role_templates`、必需角色列表 `required_roles`、环境/预算/输出 schema 目录、可引用模型、技能来源和按工作类型的解析预览；角色的 `permissions` 逐项配置资源的 `write/read/none` 或动作的 `allow/deny`，PUT 的 `deleted_roles` 显式删除角色，Manager、Coordinator 和 QA 不允许删除，`?revision=N` 返回历史配置；`POST /api/repositories/:repo/roles/resolve` 以 `role, workflow, expected_revision` 只读预览运行快照，不建任务也不落库；`GET /api/tasks/:id/roles` 查询实例、委派、各次角色运行及其快照；`POST /api/tasks/:id/roles/apply` 以 `role, expected_revision` 让运行中的角色在下一个安全检查点结束，再带新 revision 续接同一实例。沿用项目权限，正文会话不返回。`POST /api/tasks/:id/merge` 以 expected_sha、merge_method 显式授权合入已验收的 Bot PR，校验精确 head、策略与检查，不绕过 GitHub 分支规则。详见 [Role-Pool](role-pool.md)。每次角色运行还带 RoleRun 事实：`lease_scope`、`lease_epoch`、`resume_from_run_id`、`protocol_recovery`、`run_context`（不含密钥）和 `admission`，见 [RoleRun 协议](role-run.md)。

并行集成与合入：`POST /api/tasks/:id/merge` 可返回 `merged:false` 和 `integrating`／`queued` 状态，显式授权由任务引擎持久化续接；只有 `merged:true` 和 `repository_evolved` 表示确认合入。`GET` 同路径查询请求状态，`DELETE` 撤回并移除待处理队列项（已合入不撤销）。新候选需要重新验证和独立 QA。详见 [Parallel integration](role-pool.md#parallel-integration-and-durable-merge-requests-183)。

Task coordination: `GET /api/tasks/:id/coordination` reads explicit requests, notices and feedback in project scope. `POST /api/tasks/:id/coordination/:request_id/retry` retries a failed or human-wait request; task write authorization applies. See [task coordination](task-coordination.md) for role tools and version/QA boundaries.

本地聊天记录：`GET /api/channels/chats?connector_id=...` 列出管理员可见的本地群/私信及同步诊断；`GET /api/channels/chats/:id/messages` 仅查询本地密封账本，支持 `message_id,sender_id,reply_to,thread_id,from,to,keyword,cursor,limit`，时间为毫秒，limit 1–100，返回 `messages,next_cursor,has_more,sync_state,coverage,gaps,retention`。cursor 只可用于同一查询与授权范围；搜索或未命中均不调用飞书。`GET .../:id/conversation?offset=0` 按整个会话的当前读取权限分页返回历史回合、回答、阶段消息及同账本用量，不按回合来源或授权版本隐藏历史；不返回原始模型日志。群聊助手和私信的回合带 `messages`（本轮阶段消息，按顺序）；群聊助手会话另有 `can_manage`，运行中的回合有 `can_stop`。`POST .../:id/service-turns/:turn/stop`（空请求体）停止一个运行中的群聊助手回答，只限能管理该群绑定的人，返回 `{id,state}`，见[消息渠道](message-channels.md#阶段消息与停止回答)。私信拥有者可查询自己的当前授权记录，群记录仍要求群聊助手绑定的维护人（配置人、对全部范围有配置权限者）、旧群员工维护人或平台管理员，普通项目权限不会开放其他群或私信。`POST .../:id/sync` 的 `{full?:boolean}` 显式建立同步请求，未完成作业保留已有游标。`GET/PUT/DELETE .../:id/retention` 仍要求 `platform.manage`；PUT `{days:null|1..3650,expected_revision}`，DELETE `{before:<毫秒时间>,expected_revision}`，版本来自 chats 列表，清理删除原文及派生摘要并保留覆盖边界。限制和平台权限见[消息渠道](message-channels.md#本地消息账本与历史同步)。

飞书控制台读取会话采用统一入口授权：超级管理员可查看所有群聊与私聊，普通用户仍需取得整个会话的读取资格。`conversation`、`timeline`、`messages` 和 `turns/:turn` 不再按单个回合的旧来源或授权版本隐藏内容；私聊的历史管理会话一并读取。响应中的 `can_continue` 仅在本人的私聊中为真，管理员查看他人私聊不产生该用户的操作身份；关联任务的项目详情权限保持独立。

会话定时任务（#330）：`GET /api/channels/chats/:id/schedules` 返回 `{can_manage,schedules}`；`POST` 同一路径创建，接受 `{name,prompt,timezone,cron 或 interval_minutes,enabled}`。`PATCH /api/channels/schedules/:id` 带 `expected_revision` 修改上述字段，或只传 `enabled` 暂停／恢复；`DELETE` 带 `expected_revision` 删除；`POST /api/channels/schedules/:id/run` 立即运行一次；`POST /api/channels/schedules/preview` 接受时区与 `cron` 或 `interval_minutes`，返回接下来的触发时间。私聊由绑定主人管理，群由能管理群聊助手绑定的人管理；平台管理员可以查看和停用。原 `/api/channels/destinations` 与 `/api/channels/chats/:id/destinations` 已移除：项目的 `list_schedule_destinations` 直接列出可选会话（`chat:<会话 id>`），保存计划或订阅时自动登记。旧的群范围接口 `/api/channels/connectors/:id/groups` 和 `PUT /api/channels/chats/:id/personal-role` 已移除。

群聊助手绑定（#312）：`GET /api/channels/service-bindings` 返回本人可见的绑定（状态、暂停原因、可达与暂停的仓库、`can_manage`、`can_view`）、本人已绑定飞书且在本地有可信发言的候选群、可用于群聊的服务角色（`recommended` 标出仓库问答助手）、本人有配置权限的仓库和组织、服务角色权限项，以及本人维护的旧群员工（`legacy_employees`，含未结束任务数）。`PUT /api/channels/chats/:id/service-binding` 接受 `{service_role_id,scope,participation,enabled,expected_revision}`，`scope` 为 `{kind:'repositories',repositories:[项目 id…]}` 或 `{kind:'organization',organization:<租户 id>}`，`participation` 为 `mentions|questions|all`；启用要求当前个人飞书绑定、在群中（在线核验成员）以及对每个仓库或整个组织的 `config.write`，管理助手不能绑定（`service_role_not_bindable`）。停用只需 `{enabled:false,expected_revision}`，由配置人、超级管理员或对全部范围有配置权限者执行。版本冲突返回 `channel_revision_conflict`。不接受客户端给定 principal、配置人或成员证明。旧接口 `GET /api/channels/employees` 继续返回私信会话和旧群员工；`PUT /api/channels/chats/:id/employee` 只能停用旧群员工（`{project_id,enabled:false,expected_revision}`），启用返回 410 `channel_employee_retired`。详见[消息渠道](message-channels.md#群聊助手绑定)。
