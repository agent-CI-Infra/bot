# 在角色配置里调整行为

本文写给安装了这套 bot 的代码仓的管理员。bot 在一个仓库里怎样检视、打标签、开发和准备虚拟电脑，都在控制台的项目配置里调整，只有这一处来源：

| 要调整的行为 | 在哪里改 | 管理命令 |
| --- | --- | --- |
| 行为指南、检视 Issue、检视 PR、开发与跟进 bot PR、标签用法 | 内置规则是 [`docs/prompts/`](prompts/README.md) 的原文；项目自己的约定写在「角色」页 reviewer、dev 等角色的指令里，或写进 Manager 提示词（#1122 起 Manager 提示词是一整份，不再按章节覆盖） | `roles.update`、`manager.update` |
| 各角色的提示词、模型、权限和预算 | 「角色」页的各个角色 | `roles.update` |
| 检视标签、开发标签、开发中标签的名字 | 「项目设置 → 基本 → 标签」 | `project.update` 的 `review_label`、`development_label`、`developing_label` |
| 虚拟电脑的资源、软件包、环境变量和初始化脚本 | 「机器配置」 | `POST /api/environments/:id/configure` |
| 仓库自己的 skill | 仓库默认分支的 `.agents/skills/<名称>/SKILL.md` | 改仓库文件 |

项目没有写自己的约定时用内置原文，就是 [`docs/prompts/`](prompts/README.md) 下的 Markdown，见[统一任务调度与对象 Manager](workflows.md)。保存只影响之后新建的任务，已经开始的任务按开始时的配置做完。

## 仓库里的 `.bot/` 文件不再读取

早期版本从仓库默认分支读取 `.bot/guide.md`、`.bot/rules/*.md` 和 `.bot/computer.yaml`，并允许管理员在控制台给它们加「控制台覆盖」。这三层已合并成上面的单一来源（#935）：

- **升级时一次性导入**：升级后第一次启动时，每个已有项目按当时生效的那一层导入。仓库里有的规则文件写进对应的 Manager 章节，章节开头注明「由 `.bot/<文件>` 导入（提交 <SHA>）」；`labels.md` 第一行的 `review_label` 和 `issue-development.md` 第一行的 `development_label` 成为项目设置里的标签名，这一行从章节里去掉；`.bot/computer.yaml` 的字段并入项目的机器配置。导入前后 bot 的行为相同。
- 升级时还没读过仓库规则的项目，在 bot 第一次为它读取仓库时导入一次（任务开始或「刷新默认分支文件」）。升级后新加的项目不导入，从内置原文开始。
- 已经开始的任务保留它读到的规则原文，做完为止。
- 每个项目的导入结果在「角色 → Manager」的「.bot/ 规则文件导入记录」里：导入了哪些文件、写进了哪些章节、标签名、机器配置字段和需要留意的问题，审计记录为 `rules.imported`。
- 之后修改仓库里的 `.bot/` 文件不再影响 bot。仓库还留着这些文件时，项目设置和「角色 → Manager」会提示它们已迁入角色配置、可以删除；PR 改动 `.bot/` 也不再被检视总结标为「改变 bot 行为」。
- 控制台覆盖层和 `rules.update` 管理命令已删除：旧的 `PUT /api/repositories/:id/rules` 和 `rules.update` 返回 `410 rules_update_removed`，说明改用 `manager.update`、`roles.update` 和项目设置；`POST /api/repositories/:id/rules/apply-computer` 同样返回 410。
- 今后不再新增 `.bot/` 覆盖，见[开发约定](development.md)。

## 仓库 skill

`.agents/skills/` 下各级目录里的 `SKILL.md` 是仓库的 skill，bot 像普通 agent 一样读取并遵循：

- 规则从分支读，不从正在处理的 PR 的提交里读：PR 检视和 bot 按检视意见修订自己的 PR 读默认分支；Issue 检视和 Issue 开发读项目的「基准分支」（没设时就是默认分支）；继续修改 bot 已经为 Issue 开的 PR 时读这条 PR 的基准分支。
- agent 先只看到每个 skill 的名称、用途（front matter 的 `description`，没有时取第一行）和路径，做到相应工作时再读全文。只加载文本，不加载 JS 扩展，最多 32 份；单份不限大小。
- PR 改动 `.agents/skills/` 下的文件（含移动、删除）时，检视总结会写明这些文件改变了 bot 的行为，需要人来决定。
- 「角色 → Manager」的「仓库 skill」列出默认分支上的 skill，可以刷新和查看全文。

**边界**：skill 只能指导与本仓库相关的工作，不能扩大权限或改变平台规则。系统提示词写明了这一点；下面这些照常由控制面拒绝并记录，不因 skill 的内容放开：

- 读取或外发凭据、令牌：agent 只拿得到本仓库的只读令牌，没有能写入的 GitHub 凭据和模型凭据；
- 访问其他仓库：GitHub 读写工具只对本项目的仓库生效；
- 绕过平台权限、能力上限或发布通道：评论、标签、分支和 PR 只能经控制面的工具发布，每次写入按角色的 GitHub 写权限和项目能力上限检查，`github_write` 永远不能改 `.github/workflows/`；
- 修改平台配置：任务里没有管理命令。

出错时任务在准备阶段停下，状态显示「配置待补」，原因归为「仓库内容或规则」：

| 错误码 | 原因 |
| --- | --- |
| `invalid_rule_content` | `SKILL.md` 含 NUL 字节 |
| `invalid_skill_file` | `SKILL.md` 是符号链接、子模块等，不是普通文件 |
| `unsafe_skill_file` | 检出的代码里 skill 路径上有符号链接 |
| `too_many_bot_skills` | `.agents/skills/` 下的 `SKILL.md` 超过 32 份 |

修好默认分支上的文件后，等待中的任务会自动重试。规则章节原文和 skill 索引每个任务都直接交给模型，它们和任务摘要合计超过 2 MiB 时，任务停下并报 `agent_context_too_large`。早期版本因 `.bot/` 文件停下的任务（`invalid_bot_label`、`invalid_bot_computer`、`invalid_bot_rule_file`、`unsafe_bot_rule`、`bot_rule_too_large`），点「重试」即可继续。

## 检视和开发标签

在「项目设置 → 基本 → 标签」里设置，或用 `project.update` 的 `review_label`、`development_label`、`developing_label`：

- **检视标签**：检视评论发布后，控制面给 Issue 或 PR 加上这个标签。默认 `bot-reviewed`；留空表示不加。
- **开发标签**：有人（不是 App）给 Issue 加上这个标签，是[自动开发](#自动开发什么时候开始)的依据之一，比较时不区分大小写。默认 `bot-develop`，不能留空：不想让 bot 自动开发，请把项目的能力上限设在「可开发并开 PR」以下。
- **开发中标签**（#1047）：bot 开发一个 Issue 期间，控制面给它加上这个标签；PR 开出（或 bot 自己的 PR 更新）后去掉，开发没有产出 PR 就停下（失败、取消、暂停、开发标签被去掉、无需改动）时也去掉，重新开始时再加上。仓库没有这个标签时控制面先创建（颜色 `fbca04`，带说明）。不论开发的依据是标签、维护者的评论还是 Manager 的规则都加。默认 `bot-developing`；留空表示不加。开发开始时记下当时的名字，中途改设置不影响去掉哪一个。管理助手为能力上限设为 `develop` 的仓库补齐标签时会一并创建它（仓库已有时不改）。
- **已开 PR 标签**：bot 为 Issue 创建 PR，或更新了这个 Issue 对应的 bot PR 后，控制面在来源 Issue 上保留 `bot-developed`。没有产出 PR 的开发结束时不会加它。同一 Issue 之后再开发或取消开发，已有标记仍保留。能力上限设为 `develop` 时管理助手接入也会一并创建它，仓库缺少时控制面会在首次使用时创建。
- 名字最长 50 个字符，不能有首尾空白和控制字符，不合法时报 `invalid_label`。
- 模型在 `labels` 和 `development` 章节开头读到检视标签和开发标签的名字；agent 不能给 PR 选这些状态和触发标签，检视也不会把它们当分类标签加。

## 自动开发什么时候开始

项目能力上限低于「可开发并开 PR」（`develop`，见[项目能力上限](workflows.md#项目能力上限)）时不开发，新项目默认 `comment`。能力上限为 `develop` 时，开发别人开的 Issue 由项目 Manager 决定（#815），问题清晰的 Issue 默认由它自己判断开发（见下文的自主开发规则）。它在 `create_task` 里写明依据，控制面在建任务时核对，并把依据记在任务上（任务详情的「开发依据」）：

- `label`：有人（不是 App）加了开发标签；控制面读 GitHub 上最近一次加这个标签的人；
- `maintainer_request`：Issue 上的一条评论提出要求，给出评论编号；控制面核对评论在这个 Issue 上，且评论人在仓库里有 triage 或更高权限；外人的评论不能作为依据；
- `project_rule`：Manager 提示词里允许开发这类 Issue 的规则，给出原文；控制面核对原文在当前的提示词里，并记下提示词版本。

依据不成立时建任务被拒绝，拒绝原因返回给 Manager 并记在事件上；Manager 可以在 Issue 上回复缺什么。旧版 Actions 处理器登记的历史 Issue 保留原有的开发依据规则。新提报采用普通 Issue 的项目规则，见 [Actions 失败处理](actions-failures.md)。飞书群里建的、要开 PR 的任务记「群的授权档位」，私聊里建的记「请求人自己的权限」。

Issue 的打开、编辑、评论和提到 bot，有人加开发标签，以及每次检视发布（不论结论，#1104），都会把「开发 Issue」作为可以新建的工作交给 Manager；Issue 的这些更新也可以续接正在运行的开发。Manager 读 Issue、评论、最近一次检视的结论（`conclusion`）和建议（`recommendation`）、认领事实和同一 Issue 上已有的任务，决定现在开发，还是不开发并新建一次检视来回复。加标签需要仓库的 triage 或写权限，所以 Manager 把它当作维护者的决定：它能回答「bot 可不可以开始」「Issue 正文里保留或认领的工作要不要交给 bot」，回答不了还没定的行为、范围或设计问题。检视不再返回「是否需要改代码」「原句」「实现目标」「是否需要人决定」这些授权字段，也不再在评论里写「等开发标签」。

内置 Manager 提示词第 ④ 章「特性开发与缺陷修复」的「Starting development」小节有一条自主开发规则，作为 `project_rule` 依据：最近一次检视结论为「可开发」、问题已确认、推荐方案范围明确且明显优于其他方案、没有留给人决定的问题、没有与已有特性冲突、没有被别人认领时，bot 可以自行开发；开出的 PR 在说明里写明依据并 @ 报告人。能力上限是总开关：新项目默认 `comment`，不会自主开发。仓库 README 或 CONTRIBUTING 里只要求「必须由人加开发标签」的句子不否决这条规则（提示词里写明了），这样的说明应该改掉；怎么改代码、跑什么测试、用哪些已有标签，仍按仓库自己的说明和 skill。项目改写了 Manager 提示词时以项目的文本为准，删掉这条规则就不再自主开发。

**有没有被别人认领由模型判断**（#1047），控制面只提供事实，不用字符串或正则匹配评论内容：指派人；其他人打开的、GitHub 上与这个 Issue 关联的 PR（从 PR 引用了它的 cross-reference，或合入后会关闭它的 `closedByPullRequestsReferences`，标出 `closes`；bot 自己的 PR 不算）；最近 10 条评论原文（bot 自己的评论不算）。Issue 检视在上下文的 `claims` 里读到指派人和关联 PR（评论在 `comments.json`），在 `recommendation` 里写明有没有人认领、是谁、凭哪条评论、指派或 PR；认领不改变检视结论。检视发布时控制面重新读一遍，作为 `facts.development.claims` 随「检视已发布」事件交给 Manager；其他事件没有这份事实，Manager 要按规则自行开发或按评论要求开发前，用 `github_read` 自己读评论和关联 PR。有人被指派、开着处理它的 PR，或在评论里说要做、正在做（不论措辞和语言），就算认领，直到本人或维护者放弃或交给 bot；提问、+1、表示愿意帮忙测试或检视、「应该有人修」都不算。被别人认领的 Issue 不自行开发，开发标签或维护者在评论里的要求可以把它交给 bot。

开发按 Manager 写的简要说明（目标和验收标准）进行。

**开发进展只写在 Issue 上的一条评论里**（#1047）。开发开始时控制面创建这条评论，之后只编辑它，不另发评论，原来 PR 开出后单独发的 "Implemented in <PR>" 也并进来（修订 bot 自己的 PR 时仍在那个 PR 上说明）。评论只写里程碑：开始的依据和 Manager 写的目标、验收标准；开发 agent 用 `report_development_milestone` 提交的「分析与计划」（结论、自己做的设计和决定及理由、主要改动和验收）和「完成」（修改重点、测试要点）；结束时控制面填上的 PR 链接，或停下的原因和需要人做什么（agent 自己停下时用它提交的原因，控制面停下时按停止码说明，不写内部细节）。agent 只能提交这三类里程碑，不能报「正在开发」「正在测试」，也不能自己评论。评论和标签由控制面根据任务状态写到 GitHub：写失败不影响开发，记下后按 30 秒起、每次翻倍、最长 1 小时重试，连续 12 次失败后放弃；开发在运行之外结束（有人取消或暂停、Issue 被关闭）时，engine 的巡检在一秒内补上。评论末尾带 `<!-- dept-bot:development-status:<任务 ID> -->` 标记，重试时先按标记找已经发出的评论，不会发第二条。以开发标签为依据的开发在发布 PR 前会再查一次标签，被人去掉就停下（`waiting_permission`），这件事作为 `development.stopped` 事件交给 Manager，由它决定要不要在 Issue 上回复（开发的进展评论已经写明停下和重新加标签可以继续，内置规则只在有人提问时再新建检视回答，不另发评论，#1047）；有人重新加上标签时，Manager 续接这个开发，任务接着做，不用人点「重试」。以其他依据开始的不看标签。开发期间 Issue 的标题或正文被修改不会让开发停下：任务改用当前的文本，修改作为更新记下，之后开始的角色在任务事实（`updates`）里读到；Issue 的编辑、评论和提到 bot 的事件也可以由 Manager 续接到运行中的开发（内置常设规则 `issue-update` 就这样做）。已经在运行的会话实时收到更新，要等 Harness 会话层（#834）。同一 Issue 同时只有一个开发任务。`development` 章节里可以再写更严的条件（例如限定 `type`、`size`），由 bot 遵守。

## bot 开的 PR 怎样跟进修改

bot 开 PR 之前，开发任务已经让独立的检视 agent 看过改动、跑过仓库测试，并通过了独立 QA，所以 bot 自己开的 PR 和 bot 自己推的提交不再单独检视（#1104）。之后 bot 在同一个分支上继续修改，有两种来源：

- **仓库成员的意见**：在 bot 的 PR 上评论、提交检视或写行内评论（作者是 `OWNER`、`MEMBER`、`COLLABORATOR`），意见直接交给项目 Manager，由它判断：要改就建一次修订，把意见原文带给修订任务（已有修订在跑时续接给它；它开工之后才收到的意见，结束时再交回 Manager 决定是否再修订一次）；只是提问就直接回答，或者请检视看一下代码再答；批准或致谢不用处理。修订任务对每条意见再判断一次：要求修改就照做；提问、或者它认为不对的意见，在说明里给出回答和证据，不改代码。不管改没改，说明都会以评论发到 PR 上，并 @ 提意见的人。人的意见不设次数上限，同一条评论只修订一次。
- **其他检视机器人的意见**：其他 App（例如别的代码检视机器人）在 bot 的 PR 上留的意见同样交给 Manager，由它判断合不合理；控制面不限次数，Manager 能看到这个 PR 已经为意见修订过几次、其中几次来自这个机器人，由它判断是否是两个机器人在互相循环。

有人要求检视 bot 的 PR 时（例如在 PR 上提到 bot），检视照常进行；它发现的可以修改的问题也交给 Manager，由它决定要不要修订。

每次修改仍要通过项目的测试命令才会推送。这些修改只在 bot 分支上追加提交，不批准、不合并，也不会强推。

合并不在这个流程里，但不是只有人能做：Manager 默认有 Pull Request 和 Contents 写权限，可以经 `github_write` 批准 PR、写分支（包括默认分支），也可以合并 PR（目标分支要求 merge queue 时送入队列）；其他角色、群助手和管理助手按各自的 Contents 和 Pull Request 写权限。能否自行合并由项目的[自动合并策略](workflows.md#项目自动合并策略)决定（#1170）：默认 `disallow` 下只有维护者明确要求合并某条 PR 才合并，控制面核实请求来源后才发出；`non_bot_only` 和 `allow_all` 放开别人的或全部 PR。系统提示词按当前档位写合并边界。不经 PR 直接移动默认分支的写入（在默认分支上写文件、改它的 ref、`POST /merges` 合进它）按同一策略处理，`allow_all` 以下也要核实过的维护者请求；推送到别人的分支仍靠提示词约束（#1026），人明确要求时才推送并引用这条要求。这类写入不经过控制面的合并校验（候选、QA、检查），能不能合入由仓库的分支保护（或规则集）和必需检查决定，所以接入的仓库应打开这两项，见[接入指南](onboarding-guide.md#4-需要你亲手确认的事项)。不希望 Manager 合并时，在「角色 → Manager」把 Contents 改成只读。人在控制台合并走带校验的 `POST /api/tasks/:id/merge`，见[角色池](role-pool.md#authorized-merge)。

## 机器配置

在项目的「机器配置」里设置，保存后按新配置重建虚拟电脑：

| 字段 | 含义与范围 |
| --- | --- |
| `cpus` | CPU 核数，0.25–16，没写时跟随全局默认（内置 2） |
| `memory_mb` | 内存（MiB），256–65536，没写时跟随全局默认（内置 4096） |
| `pids` | 进程数上限，64–16384，没写时跟随全局默认（内置 1024） |
| `tmp_mb` | `/tmp` 大小（MiB），16–16384，没写时跟随全局默认（内置 1024） |
| `egress` | 是否允许访问外网，布尔值，默认跟随部署设置 |
| `packages` | 要安装的 Debian 包名，最多 100 个 |
| `env` | 非机密环境变量，最多 64 个；`PATH`、`HOME`、`BOT_*`、`GIT_*` 等保留名会被拒绝 |
| `setup_script` | 初始化脚本，以项目用户身份运行；内容变化后重新运行 |

环境变量对仓库代码可见，不要填写密钥。
