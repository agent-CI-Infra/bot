# GitHub 自动化：检视、开发、Actions 与 CI 改动

本文站在仓库维护者视角说明 launchpad 在 GitHub 上的全部自动化行为。底层调度、任务引擎与交付机制见 [事件分派、通用任务引擎与交付验收](../design/dispatch-and-tasks.md)。

## 1. Issue 与 PR 自动检视

仓库启用且能力上限至少为「可评论和打标签」（`comment`）时，bot 自动处理以下事件（各事件可在「项目设置 → 监听与触发」独立开关）：

- **Issue 检视**：新开 Issue、编辑标题/正文、作者或仓库成员评论，或评论中 `@bot` / `@agent-ci-infra-bot`（由 `BOT_MENTION_NAMES` 配置）时触发。
- **PR 检视**：PR 打开、从草稿转为 Ready for review、推送新提交（`synchronize`）、作者/成员发表评论或评审、或 `@` 提及 bot 时触发。草稿 PR 与已关闭对象不触发。
- **单条总结评论原位更新**：每个 Issue 或 PR 只维护**一条总结讨论评论**，后续再次检视（新提交、讨论更新、提及）直接更新该评论并递增检视次数，不刷屏；行内问题仅在可核对到真实 diff 位置时发表行内 Review，事件固定为 `COMMENT`（不批准、不请求变更、不自行合并）。
- **已修复讨论串自动关闭**：PR 再次检视时，若作者已修复本 bot 先前发表的行内意见，bot 会关闭对应讨论串并在总结评论中列出；仍未修复的意见引用原评论链接，不重复刷屏。
- **需要人工处理醒目提示**：模型标明需人工决定的发现，或 PR 修改了 `.agents/skills/`、`.pi/skills/`、根目录 `AGENTS.md`/`CLAUDE.md` 等影响 bot 行为的文件时，评论开头以 `[!IMPORTANT]` 提醒人裁定；凡需人类参与、确认或拍板的场景（检视结论需决策、开发受阻停止、Manager 求助或助手询问方案），内置提示词统一要求先讲清背景与阻塞点，存在多个可行方案时给出含推荐项的具体备选方案及各方案优缺点（单一路径阻塞则直接写明所需人工动作而不编造备选），方便维护者快速决策。
- **分类标签自动添加**：检视发布后，控制面可自动添加检视标签（默认 `bot-reviewed`）及仓库已有的分类标签（不创建未定义的分类标签，不覆盖人工已选的同维度标签）。
- **无打断续接**：检视进行中收到新评论或新推送时，不取消当前任务，而是在回合之间刷新讨论/原地推进 git worktree 到新 head 并并入上下文；若结果已发布，则在同一任务上续接下一轮。

## 2. Issue 自动开发与 PR 交付

项目能力上限设为「可开发并开 PR」（`develop`）时，项目 Manager 负责判断某个 Issue 是否开始开发。

### 开发依据（满足其一即可）

控制面建任务前会强制核验以下三种依据之一，并记录在任务详情的「开发依据」中：

1. **开发标签（`label`）**：有人（非 App）给 Issue 加上项目配置的开发标签（默认 `bot-develop`）。
2. **维护者评论要求（`maintainer_request`）**：具备仓库 `triage` 及以上权限的维护者在 Issue 评论里明确提出开发要求（外部访客评论不算依据）。
3. **项目规则（`project_rule`）**：Manager 提示词允许自主开发的规则。内置提示词默认开启「清晰问题自主开发」——当最近一次检视结论为「可开发」、问题已确认、推荐方案明确、没有留给人决定的问题且**未被他人认领**（无指派人、无他人关联开放 PR、无人在评论中认领）时，无需加开发标签即可自行开发；删掉该条规则则关闭自主开发。

### 开发过程与状态反馈

- **单条进展评论与状态标签**：开发期间控制面在 Issue 上加「开发中」标签（默认 `bot-developing`）并维护**一条持续编辑的里程碑进展评论**（包含开发依据、非默认基线分支说明、目标与验收标准、分析与计划、完成摘要及最终 PR 链接或结束/受阻原因）。任务正常结束但未开出 PR（如以报告收尾或无代码改动）时，进展评论状态显示「已结束（未开出 PR）」并展示停止说明或脱敏摘要，不再误标为开发失败或提示重试。
- **支持指定非默认目标分支**：当 Issue 面向非默认分支（如发布分支或特性分支）时，Manager 可通过 `target: { type: "issue", number, ref: "<branch>" }` 指定目标远端分支，控制面检出该分支并将其作为后续 PR 的 `base` 分支。既有 bot PR 的复用按基线判定：指名分支时只复用 `base` 与指名分支一致的开放 bot PR；未指名分支时沿用最新的开放 bot PR。两者不一致时旧 PR 原样保留（不改其 `base`/head），新交付落在按基线区分的分支名上（默认基线为 `bot/issue-<N>`，其他基线为 `bot/issue-<N>-<base>`（`/` 等字符写作 `-`），分支登记给当前任务）并在指名基线上开新 PR。只读或诊断任务还可在 `target.ref` 中指定提交 SHA 或标签，开发任务遇到不存在的分支或非分支 ref 时明确报错而不静默回退到默认分支。仓库 `.agents/skills/`、`AGENTS.md` 与 `CLAUDE.md` 仍严格只从项目可信基准分支加载。
- **默认由团队开发并独立检视**：会开 PR 的代码改动默认交给 Task Manager 团队：`dev` 实现后，Manager 在提名交付前派独立 `reviewer` 检视；行为有改动、且 `dev` 的测试覆盖不到时再派 `test`。只改文案、注释或文档的小改动可以只由 `dev` 完成，Manager 在提名时写明理由（`checks_note`，不公开）。这是内置引导而不是平台门禁，是否派人仍由 Manager 决定；Manager 提名时和 QA 验收时都能看到这个候选由哪些角色产出了结果（例如「只有 dev，没有独立检视」）。
- **验证与发布门禁**：开发在项目电脑独立工作区中改代码、跑测试；交付时控制面先固定工作树快照并核对工作区 `HEAD` 未脱离任务发布基线（非合法冲突解冲/变基场景下拒绝跨分支错发 PR），运行项目配置的 `test_command` 并经过独立 QA 核验（通过后只发布该快照，测试临时产物不进入 PR），推送 `bot/issue-*` 任务分支（同一 Issue 在不同基线上各有一条，默认基线为 `bot/issue-<N>`，其他基线为 `bot/issue-<N>-<base>`）并开 PR。
- **结果标签**：成功开出/更新 PR 后去掉 `bot-developing` 并保留 `bot-developed`；若检视发现需补充信息/需人工决定或开发受阻未产出 PR，自动加上「需人工」标签（默认 `bot-needs-human`），待恢复开发或开出 PR 后移除。
- **PR 正文与评论媒体**：开发或检视在工作区生成的截图（PNG/JPEG/GIF/WebP，单张 ≤ 5 MiB）与录屏（MP4/WebM，单段 ≤ 20 MiB），可通过工具 `media` 参数显式附带并在 PR 正文或评论中以 `workspace:<路径>` 嵌入（每次最多 8 个文件、合计 ≤ 30 MiB），由平台经公网 HTTPS 随机访问链接托管。

## 3. bot PR 的跟进修订

- **开出后不再自动检视**：bot 自己开出的 PR 与推送不会触发自动检视。开出前的团队检视、项目测试与 QA，就是人看之前全部的独立检查，所以开发默认走上面的团队流程。
- **仓库成员意见直接交由修订**：仓库成员（`OWNER`/`MEMBER`/`COLLABORATOR`）在 bot PR 上发表评论、评审或行内意见后，Manager 判断处理——需要改代码就进入修订并在原 bot 分支追加提交（不强推、不另开 PR），纯提问或不同意则带证据回复并 `@` 提意见的人。
- **其他检视机器人意见**：其他 App 留在 bot PR 上的意见同样交给 Manager 判断是否采纳，并向其展示历史修订次数以防止机器人互刷循环。
- **检查失败与合并冲突自动唤醒**：对开放的非草稿 bot PR，控制面检测到 CI 检查失败或相对目标分支出现合并冲突时，会自动唤醒对应 Issue 线程的 Manager 评估并安排修复/解冲（支持双亲合并或在 bot 自有分支上安全变基），同一运行失败或同一冲突组合严格去重。若 Manager 已在当前 `head_sha` 下将某冲突 PR 明确忽略（例如等待人工裁定或目标代码已退役），在无新人类评论、无新提交推送且环境/权限未变化前，控制面会抑制随主干每次前进重复投递冲突事件，避免无效空烧模型。
- **未合入 bot PR 低频内部巡检与复核（零外发通知）**：控制面对已启用仓库中仍开放、非草稿且当前无活跃任务的 bot PR 执行低频内部巡检（默认每 6 小时检查一次、同 PR 复核冷却 24 小时，可通过 `BOT_PR_PATROL_INTERVAL_MS` 与 `BOT_PR_PATROL_COOLDOWN_MS` 配置，重启后持久化状态不丢失），专门确认以下四类需要继续处理的信号：
  1. **环境/能力/权限变化**：当控制面能力版本升级、GitHub App 安装权限补齐（如开通 `workflows: write`）、项目策略或项目电脑环境恢复后，立即（绕过冷却）重新唤醒此前受阻或降级为报告结案的 PR，并把具体变化摘要交给 Manager 重新评估，不再机械沿用过时阻塞结论；
  2. **基线演进复核**：主干前进后导致新冲突，或此前失败的检查在基线变化后值得复测/变基；
  3. **未收尾的检视与停滞任务**：当前 `head_sha` 存在未解决的 `CHANGES_REQUESTED` 评审，或关联任务长期滞留在等待重试/环境/权限状态；
  4. **纯绿灯零打扰与严格不外发**：对无冲突、检查全绿、无未解意见的待人工合入 PR，巡检仅更新本地时间戳，不调用模型、不发事件、不发评论；全部巡检记录仅停留在控制面内部（分派记录与对象 Manager 线程），**严禁**触发飞书群聊、私聊或任何外部通知订阅，也不绕过 `auto_merge_policy` 自动合入或私自关闭 PR（若确认原问题消失或目标代码已退役，仅在 PR 上一次性说明背景与建议关闭理由）。
- **不改他人分支**：对于别人提交的 PR，bot 只检视和评论，不向作者分支推送提交或强推。

## 4. Actions 失败排查与提报

在「项目设置 → 监听与触发」启用「接收默认分支和版本标签的 Actions 失败事件」（前提：GitHub App 拥有 Actions 读权限且订阅了 `workflow_run` 事件；经 App 首次以 `comment` 及以上启动的项目默认开启）：

- **覆盖范围**：监控默认分支以及指向默认分支历史提交的版本标签上结论为 `failure` 的运行（忽略 PR 运行、取消与跳过），结合 Webhook 与后台定时窗口扫描防漏报，同一 `(仓库, run_id, attempt)` 去重。
- **调查与处理**：Manager 分派通用任务检出失败提交并读取失败 job 日志与相关代码：
  - 若确认所有失败 job 均由临时外部波动引起，可调用 `rerun_failed_run` 重跑失败作业（每个 run 限制重跑一次）。
  - 若确认为真实缺陷，先搜索已有开放 Issue，已有则补充证据，否则遵循仓库模板与规范新建 Issue（随后走常规检视/开发流程）。
  - 若发现定时 workflow 长期严重延迟，会按内置建议给出改为 bot 准点触发 `workflow_dispatch` 的优化方案。

## 5. CI 工作流改动（`.github/workflows/`）

具备开发交付权限的任务（包括控制台/管理助手新建的开发任务、Issue 自动开发任务以及 Manager 派发的 bot PR 修订任务）均可按正常 PR 流程修改 `.github/workflows/`，不再需要单独的任务级控制台强制确认；`github_write` 工具仍禁止直接写入工作流文件：

1. bot 在项目电脑内按仓库实际技术栈与脚本修改 workflow（涉及 `.github/workflows/` 或门禁设计时自动附带内置 `layered-ci-gates` Skill），经过项目测试与独立 QA 后提交候选快照。
2. 发布阶段当候选改动实际涉及 `.github/workflows/` 时，控制面仅在推送该 bot 分支前自动在 GitHub App 安装令牌中按需申请 `workflows: write` 权限；若 GitHub App 安装未开通 `Workflows: Read and write`，任务会停在 `waiting_permission` 并给出清晰的 `github_workflows_permission_missing` 权限开通提示。
3. CI 改动必须由人类维护者在 GitHub 检视并合并 PR 后才在默认分支生效（控制面 `github_write` 永不直接写 `.github/workflows/`，且即使在 `auto_merge_policy=allow_all` 下也强制拒绝合并或入队包含 `.github/workflows/` 改动的 PR）。
