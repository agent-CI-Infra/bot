# 知识文件恢复

文件正文、稳定 ID 目录、历史索引与 blob 必须一起保存和恢复。目录移动使用 `.write-history/file-tree.json` 中的 pending journal；正常重启会核对源和目标的 inode，继续未完成的移动，并且只记录一次移动版本。

## 移动归属无法确认

出现 `note_move_uncertain`，或者 pending 移动涉及的源/目标变成目录、符号链接等非普通文件时，本项目的文件与 notes 工具会拒绝全部操作。重试和重启不能解除该状态。这个范围是有意的：同卷的管理接口和任务进程共用身份目录，不能猜测哪个外部替换的文件属于旧历史，也不能让另一写入覆盖待恢复的路径。其他项目不受影响。

恢复由部署维护者执行：

1. 停止该项目的任务派发、项目电脑及访问这个知识卷的 manager 操作，确认没有其他进程写同一个卷。仅关闭浏览器不足以停写。
2. 通过项目电脑的实际挂载信息确认 notes 卷，保存当前**整个卷**的只读备份，包括隐藏的 `.write-history`、pending journal、所有历史索引和 blob。另存故障前后的文件，避免丢失外部修改。不要只备份可见正文。
3. 选择移动前已确认一致、在停写状态下生成的整卷备份。先将备份恢复到独立卷，在同版 manager/runner 的隔离环境中验证目录列表、受影响文件 ID、正文及历史版本均可读取。没有一致备份时保持项目停写，保留证据交维护者逐项核对；不要直接删除 pending、改 file ID、复制单份 catalog 或只降级镜像。
4. 验证后，在原卷仍未被访问时，用验证过的完整快照替换该项目 notes 卷内容。替换会回到备份时刻；备份后的正文和历史已在第 2 步保留，须核对后通过正常保存接口重新录入，不能把不同时间点的目录和历史混合覆盖。
5. 恢复同版 manager 和项目电脑，先读取目录、受影响文件和历史，确认不再返回恢复错误，再开放任务与写入。原故障备份保留，直到恢复结果确认。

升级到目录服务前同样需要整卷备份。回退到不支持稳定目录的旧版 manager/runner 时，恢复升级前的完整卷；不能让旧版直接写新版 catalog。
